# CloudX v1.0.1

CloudX 1.0.1 fixes what running 1.0.0 on the six-node and eight-node labs showed, and lets a server use IPv6. There is no schema change and no new service. There are **upgrade steps**, and two behaviour changes to read before you start.

## What is new since 1.0.0

**IPv6**
- A server on a network that has only an IPv6 subnet gets an address. Before, `create_port` looked only at the IPv4 subnet, so the port and the server had no address. The server record shows the IPv6 address when there is no IPv4 one, and the config drive (`network-config`) and `network_data.json` carry the address, prefix and gateway; a config drive for an IPv6-only port says `dhcp4: false` instead of waiting for DHCPv4. `local-ipv4` never returns an IPv6 address. On a network that also has an IPv4 subnet, IPv6 stays opt-in: name the IPv6 subnet in `fixed_ips`.
- A second dual-stack port on a network no longer fails with HTTP 502. IPv6 addresses held by other ports were not counted, so every port was given `::2` and OVN refused the duplicate. An IPv6 address given in `fixed_ips` is now checked like an IPv4 one: 400 outside the subnet or not an address, 409 when taken or the gateway. Before, it was accepted as it was.
- An IPv6 subnet no longer needs a gateway. Its DHCPv6 options row in OVN used an IPv6 address as `server_id`, which OVN refuses (it wants an Ethernet address); the refusal was only logged, so `dhcp_options_id` was always empty. The row is now created with a MAC, with `dhcpv6_stateless` for the stateless mode and the subnet's DNS servers, and ports are bound to it.
- The default security group has the same rules for IPv6 as for IPv4 (see "Behaviour changes").
- CLI: `cloudx subnet create` takes `--ipv6-ra-mode` and `--ipv6-address-mode` and works out the IP version from `--cidr`; `cloudx security-group rule add` takes `--ethertype`.

**Compute**
- A suspended server stays `SUSPENDED`. The worker's power-state sync, every 30 s, saw a domain suspended to disk as "shut off" and rewrote the status to `SHUTOFF`. `POST /servers/{id}/unsuspend` and `cloudx server unsuspend` restore it (`start` does too).

**Block storage**
- Deleting a volume that still has snapshots answers 409. Before, the database row was dropped and the backend volume stayed behind (on Ceph, `rbd rm` refuses an image with snapshots).
- Deleting a Ceph snapshot runs `rbd snap rm pool/image@snap`. Before, the worker ran `rbd rm` on a name that does not exist and only logged a warning, so the snapshot stayed on the cluster.
- `PATCH /volume-types/{ref}` exists (`description`, `max_iops`, `max_throughput`, `is_public`; the backend and disk type are refused with 422). `cloudx volume-type set` and the dashboard client already called it and got a 405.

**CLI**
- After `cloudx auth login --auth-url`, later commands find the auth API without `CLOUDX_AUTH_URL`. The address was written to `~/.cloudx/config` and never read back, so away from the controller every command went to `127.0.0.1:8005`. `CLOUDX_AUTH_URL` still wins when set.
- `cloudx server volume attach` and `detach` go through block-store (they were answered with HTTP 422). `cloudx subnet create --dns-nameserver` sends a list (it was a 422 too).

**Documentation and checks**
- A tutorial for a highly available control plane with LVM and Ceph volumes, and the docs organised by deployment and storage backend.
- `docs/feature-comparison.md` was rewritten against the code, and a test (`scripts/check_feature_comparison.py`) fails when it names an endpoint that is not a route.

## Behaviour changes to read first

1. **The default security group opens IPv6 ssh and ping.** `networking-api` adds IPv6 rules to the default group when it starts: egress to `::/0`, and ingress for ssh (22/tcp) and ICMPv6 from anywhere, under the same two switches as IPv4. After the upgrade, a server that has an IPv6 address accepts ssh and ping over IPv6 from anywhere, as it already did over IPv4; before, IPv6 traffic was dropped. Only a server on an IPv6-only network, or one whose port asked for IPv6 in `fixed_ips`, has such an address. To keep the rules from being added, put this in `/etc/cloudx/networking-api/networking-api.conf` on the controllers **before** upgrading `cloudx-networking-api`:

   ```ini
   [DEFAULT]
   default_security_group_allow_ssh = false
   default_security_group_allow_icmp = false
   ```

   Only the egress rule is added then. The switches decide what is added, not what stays: rules already in the group are removed with `cloudx security-group rule delete`.
2. **A network with an IPv6 subnet and no IPv4 subnet now gives its ports an address**, where before the port had none. Nothing else changes for networks that have an IPv4 subnet.

## Upgrading

Order: the controller first, then the compute and storage nodes. Every node must have all of its CloudX packages at one version, because each package depends on `cloudx-common` of exactly the same version. A 1.0.1 controller with 1.0.0 compute nodes works; an IPv6-only server is only set up correctly once the compute node runs 1.0.1 too (the worker writes the config drive and reports the address).

### From 1.0.0 `.deb` packages

1. Download the packages of the release and check them (`docs/deb-install.md` section 3, "Downloading a release").
2. On each node, list what is installed and install the new version of exactly those packages in one command. `--force-confold` keeps your configuration files:

   ```bash
   dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'cloudx-*' | awk '$1 ~ /^ii/ {print $2}'
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-common_*.deb ./cloudx-<each package from the list>_*.deb
   ```

   The package scripts restart the units that were active and leave disabled units disabled. Running VMs are not stopped: QEMU does not run under a CloudX unit.
3. No `cloudx-manage db sync` and no catalog sync are needed, since nothing changed in the schema or the services. Running them does no harm.
4. `systemctl list-units --failed 'cloudx-*'` must list nothing. On the controller, `cloudx security-group rule list default` now shows the IPv6 rules (unless you turned them off).

From 0.8.x or the tarball, do the 1.0.0 upgrade first (`docs/releases/v1.0.0.md`), then this one.

## What was tested, and what was not

- The unit and packaging tests pass on the release commit, and CI builds every package.
- On the 1.0.0 lab, on 2026-10-29, with the changed files installed temporarily on one controller and one compute node and then put back (hashes checked against 1.0.0):
  - `suspend` kept `SUSPENDED` for 149 s; `unsuspend` brought the VM back in 4 s and answered 409 on an active server; `resume` and `start` on a suspended server worked; a plain `stop` stayed `SHUTOFF`.
  - Three dual-stack ports got `::2`, `::3` and `::4`; an explicit IPv6 address that was taken, outside the subnet, the gateway or not an address was refused (409, 400, 409, 400); a deleted port's address was handed out again.
  - `PATCH /volume-types` changed the mutable fields only (422 for the backend, 404 for an unknown type).
- **Not run on a running cloud**, only by unit tests: an IPv6-only server end to end (no VM was booted; the `network-config` that is written was checked, a guest was not), the DHCPv6 row and its binding against OVN, the IPv6 rules of the default group and their ACLs, `cloudx auth login --auth-url` followed by other commands from another machine, and the three block-storage fixes (the bugs were found on the lab, the fixes are covered by unit tests).

After installing 1.0.1 on a lab, these are worth a look:

```bash
cloudx network create v6net
cloudx subnet create v6sub --network v6net --cidr fd42:7:7::/64
cloudx server create vm6 --image cirros --network v6net      # cloudx server list shows fd42:7:7::2
cloudx security-group rule list default                      # egress, ssh and ICMP for both families
```

In the guest, `ip -6 addr` shows the address; `ping6` and `ssh` from a second server on the same network use the default group. On a controller, `ovn-nbctl list DHCP_Options` shows a row for `fd42:7:7::/64` whose `server_id` is a MAC, and `ovn-nbctl lsp-get-dhcpv6-options <port>` shows it bound.

## Known limitations

- No router advertisements: nothing sets `ipv6_ra_configs` on router ports, so SLAAC does not work. A guest gets its IPv6 address and prefix from the config drive, which cloud-init images read; an image without cloud-init does not learn it.
- Floating IPs are IPv4 NAT. The dashboard has no Unsuspend action and no page for trunks, QoS policies or subnet pools.
- The limits in `docs/quickstart.md` ("Known limitations") and `docs/deb-install.md` section 8 still apply.
