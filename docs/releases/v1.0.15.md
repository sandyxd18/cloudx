# CloudX v1.0.15

CloudX 1.0.15 is the first release after 1.0.11. It adds live migration of running servers and `cloudx host drain`, makes the browser console proxy able to serve https, applies a volume type's IOPS and throughput limits to LVM and NFS volumes, and fixes five problems found on the 8-node lab: the metadata service for servers behind a router, security group rules that name a remote group, Kubernetes clusters that went `ACTIVE` before their workers joined, and volumes stuck in `creating`.

## What is new since 1.0.11

**Compute**
- Live migration. `cloudx server live-migrate SERVER [--host NODE]` (`POST /servers/{ref}/live-migrate`) moves a running server to another compute node; it used to answer `501`. The policy action is `compute:server:live_migrate`, `role:admin` by default. Disks on Ceph RBD and LVM volumes that the target reaches over iSCSI can move; there is no block migration. A migration that fails before it completes is rolled back and the server is `ACTIVE` on the source again, with the reason in `os-instance-actions`. Expect a network pause of one to three seconds and no zero-loss guarantee.
- `cloudx host drain NODE [--dry-run] [--timeout SECONDS]` disables a compute node and moves its servers away one at a time (live migration for `ACTIVE`, cold migration for `SHUTOFF`). A server it cannot move, such as one with a local LVM volume on that node, is skipped and listed, and the command exits non-zero. `cloudx host enable NODE` puts the node back in service.
- `cloudx-setup-migration-ssh [--dry-run] NODE...` (in `cloudx-cli`) prepares the root ssh trust between the compute nodes that live migration needs.
- Six optional compute worker settings: `live_migration_host`, `live_migration_uri`, `live_migration_timeout` (1800), `live_migration_max_downtime_ms` (300), `live_migration_bandwidth_mbps` (0, no cap) and `live_migration_auto_converge` (false). An empty `live_migration_*` value means the default; before, an empty number stopped the worker at start.
- Instance HA never evacuates a server that is `MIGRATING` on its own: it records it as `skipped` with the reason, because the guest may already run on the live-migration target. An operator decides (`docs/live-migration.md`). `POST /servers/{id}/evacuate` accepts a `MIGRATING` server once its source node is forced down.
- A volume type's `max_iops` and `max_throughput` now limit LVM volumes and NFS file volumes too. Before they were applied only on Ceph. The compute node sets them as a libvirt `<iotune>` when the volume is attached and when the server is built.
- The browser console proxy can serve https. Set `console_proxy_cert` and `console_proxy_key` in `compute-worker.conf` and restart `cloudx-compute-worker`; the console link then starts with `https://`. Without the settings nothing changes.

**Networking**
- The metadata service (`169.254.169.254`) answered `404` to every server that came through a router, because the router's NAT rewrote the request's source address. networking-api now exempts the metadata address from NAT on every router.
- Security group rules that name a remote group (`remote_group_id`) now work between members on different compute nodes. Before, two servers of the same group could talk only when they shared a node.

**Kubernetes**
- A worker no longer reports ready before it has joined. A cluster whose worker cannot join now ends in `ERROR` at `ready_timeout` with the reason, where it used to be `ACTIVE` with only the master in the Kubernetes API.
- Each cluster gets its own security group `k8s-<cluster id>`, deleted with the cluster. The nodes used the project's default group, which blocked the workers from the master's port 6443.

**Block storage**
- A volume whose create request was lost (a broker without quorum, a worker that died first) no longer stays in `creating` forever. After `VOLUME_CREATING_TIMEOUT_SECONDS` (default 3600, `0` switches the check off) with nothing on the backend, the reconciler marks it `error`.
- A volume that is already `error` keeps the message it has. The reconciler used to mark it again on every pass of every worker, and the generic `Physical storage object missing on node` replaced the stored reason, such as the one a failed create wrote.

**Documentation**
- `docs/tutorials/ha-control-plane.md` explains how to make RabbitMQ drop the connections of a controller that was powered off (TCP keepalive and a user timeout in `advanced.config`), and lists the controller power-off tests with their measured gaps.

Live migration also has several smaller fixes (an IPv6 `live_migration_host`, Ceph servers that failed with `Secret not found`, late reports of an earlier migration, deleting a Kubernetes cluster during a migration); `CHANGELOG.md` lists them.

## Behaviour changes to read first

1. A volume type that sets `max_iops` or `max_throughput` and is used by LVM or NFS volumes starts to throttle them: at the next attach for a data volume, at the next build for a root volume. A volume already attached to a running server keeps its old limit until then.
2. Live migration needs ssh between the compute nodes. `cloudx-setup-migration-ssh` gives every compute node root access to every other one. It also needs TCP 22 and 49152-49215 open between the compute nodes and a different iSCSI initiator name on each node. `docs/live-migration.md` has the details.
3. The upgrade replaces the `cloudx-novnc-proxy` unit file: it now starts `python -m console_proxy`. If you changed the unit, redo the change.
4. New Kubernetes clusters count one security group against the project's quota. Clusters made before keep the default group and are not changed. `callback_url` in the Kubernetes worker's conf must still be an address the servers can reach (`docs/k8s-engine.md`).
5. Existing routers and floating IPs get the metadata fix when networking-api starts. The remote group fix reaches an existing rule at the next change to its group's rules or ports; to apply it at once, restart networking-api and add or remove any rule of the group.
6. A volume that has been `creating` for more than an hour with nothing on the backend becomes `error` on the next reconciler pass. Delete it and create it again. Set `VOLUME_CREATING_TIMEOUT_SECONDS=0` in the block-store worker's environment to keep the old behaviour.

## Upgrading

No schema change and no `cloudx-manage db sync`. From 1.0.11 `.deb` packages, install the new version of every CloudX package on each node in one command with `apt install -o Dpkg::Options::=--force-confold`, as in `docs/releases/v1.0.2.md` "Upgrading"; every node must have all of its CloudX packages at one version. Update the compute nodes first, then the controllers. Install `cloudx-networking-api` before `cloudx-k8s-engine-worker` or in the same pass, because the worker now asks networking-api for the cluster's security group. Running VMs are not touched. Check `systemctl --failed` on each node afterwards. The `cloudx` CLI is not in the `.deb` files: update it where it is installed (`scripts/install-cli.sh`) to get `live-migrate`, `host drain` and `host enable`.

To use live migration, follow the prerequisites in `docs/live-migration.md` before the first migration.

## What was and was not tested

Unit tests for every change in this release.

Lab, 2026-11-27, 8-node Proxmox lab (three controllers, three Ceph nodes, two compute nodes):
- **The 1.0.15-1 packages:** all 47 `.deb` files were built from the release commit and installed with apt on the three controllers and the two compute nodes, one node at a time, over 1.0.11-1 packages that carried hand-patched files for the three networking and Kubernetes fixes (the networking-api and block-store worker files that were compared afterwards match the release source). No failed unit on any node, Patroni, RabbitMQ and Ceph healthy after each controller, the two running servers kept running.
- **Metadata:** servers on both compute nodes, behind a router with a floating IP, answer `200` with their own instance id.
- **Remote group:** a server in a group with the rule `ingress tcp 5000 from the group itself` on one compute node reached a listener of the same group on the other node; a server outside the group did not. Egress and IPv6 rules that name a remote group were checked earlier the same day.
- **Kubernetes:** a cluster with one master and one worker became `ACTIVE` after both reported ready, with its security group; deleting it removed the VMs, the group and the record in about 13 seconds. The first attempt ended in `ERROR` because the master could not reach `callback_url` (in this lab the controllers answer provider-network sources through the wrong gateway); it worked after a route on the controllers.
- **Stale `creating` volumes:** with `VOLUME_CREATING_TIMEOUT_SECONDS=120`, the block-store workers stopped and the create message purged from the `block-store` queue, the volume went to `error` about 144 seconds after it was created; a volume created normally afterwards was `available` and untouched. The message of that volume was the generic text, not the one the check writes, which is what the change above fixes; it was found on the lab and the fix itself was run in unit tests only.
- **Live migration and `host drain`:** run earlier the same day on builds of the branches that were merged afterwards, not on these packages: Ceph and LVM root disks, data volumes, drain of two to eight servers, rollback when the migration ports were blocked, a worker restart in the middle of a migration, auto-converge, an IPv6 `live_migration_host` and the nodes of a k3s cluster. `docs/live-migration.md` lists the figures; the network pause was 0.6 to 0.8 seconds.
- **RabbitMQ keepalive settings** from the HA tutorial: applied to the three lab controllers, and a powered-off controller's connections were gone after 49 seconds.
- **Instance HA and `ha-watchdog`** (on the 1.0.15-1 packages, two compute nodes, one protected CirrOS server with an LVM root on the other node; the watchdog was configured and started for the test): with ha-api cut off (`iptables` `DROP` of port 8020) from both nodes for 56 seconds, both watchdogs held at 45 seconds, nothing was destroyed and both hosts stayed `up`. With only the node of the protected server cut off, its watchdog destroyed the domain at 45 seconds, ha-api marked the host `suspect` at 82 s and `fenced` at 116 s, the recovery (started 55 s after the destroy) was `done` and the server was `ACTIVE` on the other node; an unprotected server on the same node was not touched. After the manual recovery (`forced_down` false, `cloudx ha reset`) the host was `up`, the watchdog removed its fence flag and compute-worker removed the stale domain. With a protected server that was being migrated away from the cut-off node (migration held at 1 MiB/s), ha-api recorded the recovery as `skipped` with the `MIGRATING` reason, as designed, but the watchdog destroyed the source domain at 45 seconds and the migration failed, so no copy of the guest ran until an operator settled the server (see Known limits).
- **https console proxy** (on the 1.0.15-1 packages, one compute node, a self-signed certificate for its name and address): with the three settings the proxy answered https only and refused plain http on port 6080; the certificate verified for the name and the address; the console link started with `https://`; a websocket request with a real console token got `101` and the VNC banner, and one with a wrong token did not. With only the certificate set, and with a key file that did not exist, the proxy did not start, nothing listened on 6080 and the journal gave the reason. With the settings removed the proxy served http again.
- **LVM `<iotune>` limits** (on the 1.0.15-1 packages): a volume of a new LVM type with `max_iops` 300 and `max_throughput` 2 got `total_iops_sec` 300 and `total_bytes_sec` 2097152 on its disk when it was attached, and 16 MB took 8 seconds to read and to write from inside the server, against under a second on the `gp2` and Ceph disks. After the type was changed to 4 MB/s the attached disk kept 2 MB/s, and a new attach got 4194304. A server built with a `gp2` LVM root volume (reached over iSCSI) got 3000 and 131072000 on its root disk. The Ceph disks of the same server had no `<iotune>`.

Not tested on a lab: the `<iotune>` limits on NFS file volumes, a browser with the https console, an upgrade from a clean 1.0.11 install (the lab's 1.0.11 had the hand-patched files above), a lock on a server during a drain, and more than two compute nodes.

Known limit found by the HA run: the watchdog does not know about live migration. If the node of a protected server is cut off from ha-api while the server is migrating away, the watchdog destroys the source domain, the migration fails, and the server stays `MIGRATING` with no running guest until an operator settles it (`docs/live-migration.md`, "Settling a server that stays `MIGRATING`"). ha-api itself does the right thing and does not evacuate it.

Known limit found by the HA run: a server with a Ceph RBD volume cannot be protected today (`422 server volumes could not be located`, because a Ceph volume has no host in CloudX). Only servers whose volumes are LVM volumes on other compute nodes can. `docs/ha.md` says so now.
