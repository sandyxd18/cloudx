# CloudX v0.7.19

Builds on v0.7.18 and turns the Fase 3 stubs into real features (volume replication, VPC peering, VPNaaS, BGP, K3s engine). There are **upgrade steps**.

## Upgrading from v0.7.18
1. Run `cloudx-db-migrate` on the controller: `networking_0005` (peering), `networking_0006` (VPN), `networking_0007` (BGP), `k8s_engine_0002`, `image_0003` (BIGINT sizes). Create the `cloudx_k8s_engine` database first if it is missing.
2. Copy the new `services/` (including `services/shared`) and `cli/` to every node and restart all services and workers (compute, storage and controller).
3. New units: `cloudx-vpn-worker` and `cloudx-bgp-worker` (compute and storage; need strongswan and bird2), and `cloudx-k8s-engine-worker` (controller; conf in `/etc/cloudx/k8s-engine-worker/k8s-engine-worker.conf` with `k8s_engine_api_url`, `compute_api_url`, `callback_url`, `vm_image`, `master_flavor`, `worker_flavor`, `ready_timeout`). Build the K3s image with `scripts/build-k3s-image.sh` (see `docs/k8s-engine.md`).
4. `callback_url` must be an address the tenant VMs can route to. Without a route from the tenant network to the controller, K3s clusters never become ready.
## Changes
- **Volume replication**: cross-host replica of an LVM volume (full copy over an HMAC-authenticated stream), promote/failover; CLI `cloudx volume enable-replication`, `sync-replication`, `failover`, `disable-replication`.
- **VPC peering**: same-project peering between two networks with static routes through OVN (`networking_0005`).
- **VPNaaS**: site-to-site IPsec (strongswan) per router, run by `cloudx-vpn-worker` (`networking_0006`).
- **BGP**: BIRD 2.14 speaker per router in netns `qbgp-<id>`; advertises prefixes and installs learned routes into OVN (`networking_0007`, `docs/bgp-dynamic-routing.md`).
- **K3s engine**: `cloudx cluster create` builds real K3s clusters in CloudX VMs (master, workers, scale, delete, kubeconfig). Live: 1 master + 1 worker reached `ACTIVE`, 2 nodes Ready, scale 2 and 0, delete leaves nothing behind (`docs/k8s-engine.md`).
- **Bugs found while testing K3s**: images over 2 GiB failed to upload (int32 size); Ubuntu VMs got no IP because network-config named the NIC `eth0` (now matched by MAC); `log_action` rejected the internal token on every `/servers/{ref}` route; deleting a K3s cluster violated a foreign key on Postgres; the block-store reconciler marked volumes still in `creating` as error.
- **Verification**: K3s, replication, VPN, peering and BGP live-verified on the lab (BGP data plane through a learned route was not). Local test suite: 469 tests passing.

## Known limitations
- LB: ALB HA is active/standby failover (~35 s outage, in-flight connections dropped), not full hitless active/active HA. NLB `ROUND_ROBIN` / `LEAST_CONNECTIONS` are hash-based (OVN has no connection counter; use an ALB).
- Domains are labels only (no isolation boundary).
- No dashboard pages for stacks, LB, alarms, or role assignments.
- Replication: full copy on every sync (no incremental or scheduled sync); one replica per volume, no auto-failback; stream authenticated but not encrypted, receiver has no TLS; `async`/`sync` are labels; thin-LV snapshot path untested; `replication_peers` is set by hand in the worker conf (empty = loopback only); empty `internal_token` disables the receiver; nonce cache is per process; promote is not atomic; after failover the old source LV is orphaned.
- VPC peering: same project only, no accepter approval, static routes only, max 16,384 peerings.
- VPNaaS: PSK only, stored in plaintext and returned by `/config`; one host per gateway (no failover); no remote-access VPN, BGP over IPsec or DPD tuning; `peer_address` needs manual two-sided creation; the outer IP uses one external-pool address; router needs an external gateway.
- BGP: eBGP IPv4 only, peer must share L2 with the external network; one host per speaker; MD5 password in plaintext; no BFD, IPv6, custom route-maps or graceful restart; default routes and prefixes overlapping router subnets from peers are ignored; return traffic to SNAT'd prefixes depends on reply symmetry and the data plane was not tested live; the speaker uses one external-pool address.
- Routers: the gateway chassis is the first SB chassis, not the compute gateway; `lrp-set-gateway-chassis` is manual. A new router gateway falls back to the same SNAT IP as `router1`.
- K3s engine: no HA control plane, upgrades or autoscaler; image built by hand and K3s version tied to it; tokens plaintext in the DB and TLS not verified; flavor and image come from the worker conf, not the template; VMs land in project `admin`; no SCALING timeout; callback matches nodes by role and IP with a first-unready fallback; CSI/CCM not wired to a real cluster; VMs must reach the controller API (the lab needed a temporary `172.17.0.1` on `br-ex` plus masquerade on compute); `kubectl` from the master was not run, only direct API calls.
- Worker `main.py` files on the nodes are world-writable while running as root (old install pattern).
- Scheduled snapshots remain a control-plane record only.
- Installer scripts not verified on a VM; `tests/scripts` fail on Windows (CI/WSL only).
