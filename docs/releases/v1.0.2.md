# CloudX v1.0.2

CloudX 1.0.2 fixes what an Ubuntu 24.04 guest showed on the 1.0.1 lab: a server on several networks only had one NIC, and a server on a dual-stack network could not get an IPv6 address from `server create`. There is no schema change and no new service. There are **upgrade steps** (below), and one behaviour change to read first.

## What is new since 1.0.1

**Compute**
- A server created on several networks (`networks` in the create request) gets one NIC per port. Before, the extra ports were allocated and recorded as attached, but only the primary one was plugged, so the guest had a single NIC and `cloudx server port add --port <that port>` answered 409 "already attached". The extra NICs are also plugged when a server is evacuated to another host, a failed build removes their taps, and deleting the server removes them (they were left behind).
- `network-config` configures the extra NICs: `eth1`, `eth2`, ... in the order of the networks, matched by MAC address, with the addresses networking-api allocated (IPv4, IPv6 or both) and DHCP for a port that has none. Only `eth0` gets a default route. Output for a server with one port is unchanged. A port added later with `cloudx server port add` is hot-plugged and is not in `network-config`: configure it inside the guest.
- `cloudx server create --ipv6` (`"ipv6": true` in the create request) gives the server an IPv6 address on every one of its networks, next to its IPv4 one. Before, IPv6 on a dual-stack network needed a port made by hand with `fixed_ips`, hot-attached afterwards. A network with no IPv6 subnet makes the request fail with 400 before the root volume is created. Without the flag nothing changes.

**Documentation**
- `docs/cloud-init.md` and `docs/ipam.md` describe the two changes above.

## Behaviour changes to read first

1. **A server created on several networks now has several NICs.** Before, it had one, whatever the request said. Servers that already exist keep the NIC they have: their extra ports stay recorded but unplugged, and this release does not repair them.

## Upgrading

Order: the controller first, then the compute nodes. Every node must have all of its CloudX packages at one version. The NIC change is in `cloudx-compute-worker` (compute nodes), the `ipv6` option in `cloudx-compute-api` (controller) and `cloudx-cli`.

### From 1.0.1 `.deb` packages

1. Download the packages of the release and check them (`docs/deb-install.md` section 3, "Downloading a release").
2. On each node, list what is installed and install the new version of exactly those packages in one command. `--force-confold` keeps your configuration files:

   ```bash
   dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'cloudx-*' | awk '$1 ~ /^ii/ {print $2}'
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-common_*.deb ./cloudx-<each package from the list>_*.deb
   ```

   The package scripts restart the units that were active and leave disabled units disabled. Running VMs are not stopped: QEMU does not run under a CloudX unit.
3. No `cloudx-manage db sync` and no catalog sync are needed. Running them does no harm.
4. `systemctl list-units --failed 'cloudx-*'` must list nothing.

From 1.0.0 or older, do the 1.0.1 upgrade first (`docs/releases/v1.0.1.md`).

## What was tested, and what was not

- The unit and packaging tests pass on the release commit, and CI builds every package. The two changes have their own tests (`tests/compute_worker/test_extra_nics.py`, `tests/compute/test_dual_stack_server.py`, `tests/cli/test_server_create.py`).
- **Found on the 1.0.1 lab (2026-10-30) with the Ubuntu 24.04 cloud image**, which is what led to this release: an IPv6-only server configured from `network-config` (address, /64, default route through the gateway, ping to the gateway and to a server on another compute node, ssh over IPv6); a dual-stack NIC configured from the `network-config` of a real port (both addresses, both gateways, DNS); a DHCPv6 client in the guest got exactly the address networking-api had allocated; `network_data.json` of an IPv6 port is parsed by cloud-init into the same address, prefix and route. The two bugs fixed here were found in the same run.
- **Not run on a running cloud yet (rc1):** the two fixes themselves. This section is updated with what the lab shows after 1.0.2~rc1 is installed there.
- Not tested: evacuation of a multi-network server, and servers that existed before the upgrade.

## Known limitations

- No router advertisements: a DHCPv6 client gets its address as a /128 and no on-link route or gateway, so it cannot reach its neighbours. Only the static `network-config` makes IPv6 work (see 1.0.1).
- The default `user-data` creates the user `cirros` only, so on an Ubuntu image there is no `ubuntu` user; pass your own `--user-data` to keep the image's default user.
- compute-worker waits 300 s for the root volume. Importing a large image into Ceph can take longer (a 600 MB Ubuntu image took about 17 minutes on the lab), and the server then goes to `ERROR` although the volume becomes available later.
- `cloudx server create` takes one `--network`; several networks need the API.
- netplan 1.x warns that `gateway4` and `gateway6` are deprecated. They still work.
- The limits in `docs/quickstart.md` ("Known limitations") and `docs/deb-install.md` section 8 still apply.
