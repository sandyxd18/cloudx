# CloudX v1.0.8

CloudX 1.0.8 fixes six things that a lifecycle sweep found on the lab with 1.0.7~rc1: a resize to a bigger flavor that ended in `ERROR`, a `shelve` that did not offload anything, a `live-migrate` that left the server in `MIGRATING`, a server snapshot that failed on every server, a server delete that left snapshots behind, and a lock that covered three actions. The changes are in the compute, block-store and image services and in their workers. There is no schema change, no new service, and no change in the CLI. There are **upgrade steps** (below), and several behaviour changes to read first.

## What is new since 1.0.7

**Compute**
- **Resize to a larger flavor works.** libvirt refuses to hot-plug a vCPU or memory past the maximums a domain was defined with, and CloudX defined every domain with its own flavor as the maximum. The server went to `ERROR`, with the new flavor already in the database. Inside the maximums the change is still live. Beyond them the worker writes the new size into the persistent definition as its limits and restarts the guest: an ACPI shutdown first, a destroy after 30 seconds without an answer (`RESIZE_SHUTDOWN_WAIT` in the worker environment changes the wait), then a start from the new definition. A stopped server is redefined and stays stopped.
- **`revertResize` restores the flavor name.** Resize stored the flavor id in `server.flavor` where create stores the name, so the revert looked the old flavor up by a name that is not its key and left the new flavor's name on the server. Resize now stores the name. The revert no longer sets `ACTIVE` itself; the worker does when the old size is back.
- **`shelve` offloads the server.** It posted to a block-store route that does not exist and logged the 404 as a warning, so the server was stopped and called `SHELVED_OFFLOADED` while its domain, taps and iSCSI sessions stayed on the node and its placement allocation stayed claimed. The worker now removes the domain, the taps and the volume sessions, and the placement allocation is released when the shelve ends. The ports and the volumes stay on the server record. No image is made: the root volume is the state.
- **`unshelve` builds the domain again** on a node that placement picks (the same node or another), with the same ports and data volumes, by the path that `evacuate` takes. With no node able to take the server the answer is 409 and the server stays shelved.
- **`live-migrate` answers 501** and changes nothing. The worker read `server_id` where the API sends `id`, so the request left the server in `MIGRATING` until a `start`, and it never moved a server. Live migration is planned and is not built. `POST /servers/{ref}/migrate` (cold) and `evacuate` are the supported ways to move a server.
- **Lock covers every action that changes a server.** Before, only delete, shelve and unshelve checked it. Now start, stop, reboot, pause, resume, suspend, unsuspend, resize, confirm and revert resize, rebuild, rescue, unrescue, set password, adding and removing a port, and attaching and detaching a volume answer 409 to a member when the server is locked. Attach and detach through `/volumes/{ref}/attach` and `/detach` (block-store) check it too, because block-store reaches compute-api with the internal token, which acts as admin. Admins and services still bypass the lock, and snapshots and reads stay open.

**Block storage and image**
- **`cloudx server snapshot` works.** It asked image-api to import the snapshot from a path. A volume-backed server (every server) has no such file, the snapshot had no path yet when the call was made, and image-api only reads regular files on its own node, so the call failed with 404 "source image path not found" and left a volume snapshot behind. Now block-store snapshots the root volume (`POST /volumes/{ref}/upload-image`, modelled on Cinder's `os-volume_upload_image`). The block-store-worker on the node that holds the volume exports the snapshot, converts it to qcow2, uploads it to image-api as a private image of the server's project, and removes the volume snapshot it made.
- **Deleting a server keeps a root volume that has snapshots.** The internal volume delete that a server delete uses did not have the "volume has snapshots" check of `DELETE /volumes`. The row went and the RBD image and its snapshot stayed on Ceph; on LVM the snapshot record went to `error`. Now the server is deleted and the root volume stays `available` with its snapshots until you delete them.
- **Two Ceph bugs found on the way.** `rbd export` refuses to write over a file ("File exists") and the worker handed it a temporary file it had just made. And a volume created from an image of exactly the volume size failed with `rbd: new size is equal to original size`, which stopped a server from being built from its own snapshot (the image is always the size of the root volume).
- image-api accepts a `project_id` form field on `POST /images` from a service holding the internal token, so a service can upload an image for a user's project. A user cannot name another project.

## Behaviour changes to read first

1. **`POST /servers/{ref}/snapshots` answers 202, not 201, and the image does not exist yet.** The body has the volume snapshot (`creating`) and `"image": {"name": ..., "status": "queued"}`. The image appears in `cloudx image list` as `saving` and then `ACTIVE` when the upload ends (12 s for a Ceph root volume of a CirrOS guest, about 2 minutes for an LVM one in the lab). A name that an image already has is refused with 409 before anything is snapshotted. If the export or the upload fails, no image appears and the volume snapshot stays in `error` with the reason (`cloudx snapshot list`, `cloudx snapshot delete`). A script that read the image from the answer must wait for it. On LVM the snapshot has a copy-on-write area of 20% of the volume, so a guest that writes more than that while the export runs invalidates the snapshot and the upload fails; run it again.
2. **`live-migrate` is a 501.** Anything that called it got a server stuck in `MIGRATING`; now it gets an error and the server is untouched.
3. **A locked server refuses more.** A member who locked a server and then tries to stop it gets 409 until the server is unlocked (`POST /servers/{ref}/unlock`). Automation that runs as a member user against a locked server breaks; run it as admin or unlock first.
4. **A shelved server holds no vCPU or memory** on any node, so placement shows the capacity as free. An unshelve needs capacity again and can answer 409.
5. **Deleting a server whose root volume has snapshots leaves the volume.** It shows up as `available` in `cloudx volume list` until you delete the snapshots and the volume.
6. **A resize to a larger flavor restarts the guest.** The guest is shut down and started again, so it is down for the length of a reboot. A resize inside the old maximums is still live.
7. **No `VERIFY_RESIZE`.** A server is `ACTIVE` right after a resize, as before. `confirmResize` and `revertResize` still work until the resize is confirmed.

## Upgrading

Order: the controllers first (compute API, block-store API, image API), then the compute nodes (compute worker, block-store worker). Every node must have all of its CloudX packages at one version. Running VMs are not stopped: QEMU does not run under a CloudX unit.

### From 1.0.7 `.deb` packages

1. Download the packages of the release and check them (`docs/deb-install.md` section 3, "Downloading a release").
2. On each node, list what is installed and install the new version of exactly those packages in one command. `--force-confold` keeps your configuration files:

   ```bash
   dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'cloudx-*' | awk '$1 ~ /^ii/ {print $2}'
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-common_*.deb ./cloudx-<each package from the list>_*.deb
   ```

   The package scripts restart the units that were active and leave disabled units disabled.
3. No `cloudx-manage db sync` and no catalog sync are needed. Running them does no harm.
4. `systemctl list-units --failed 'cloudx-*'` must list nothing. Check that the version took: `dpkg-query -W cloudx-common` on each node.

During the upgrade, between the first controller and the last compute node, do not shelve, unshelve or snapshot a server, and do not resize to a larger flavor:

- A new compute API with an old compute worker sends `unshelve` as a build. That is fine. An old compute API sends `unshelve` as the old message, which a new worker no longer has, so nothing carries it out and the server stays `UNSHELVING`.
- A new block-store API with an old block-store worker makes a plain volume snapshot for `upload-image`: the snapshot stays and no image appears.
- An old compute worker does the live resize only, so a resize beyond the maximums still ends in `ERROR` until the node is upgraded.

These mixed-version cases come from reading the code; they were not tried.

A server that is `SHELVED_OFFLOADED` from before the upgrade was shelved by the old code: its domain is stopped but still defined on its node, and its taps, sessions and placement allocation are still there. Unshelving it with 1.0.8 builds it again through the normal path. That case was not tested (see below); if you have such servers, unshelve one first, and if it fails on the stale domain, remove the domain with `virsh undefine` on its node and try again.

From 1.0.6 or older, do the earlier upgrades first (`docs/releases/v1.0.7.md`, `docs/releases/v1.0.6.md`).

## What was tested, and what was not

- The unit tests pass on the changed code, and CI builds every package. Each change was written test first and watched fail for the right reason. The tests run against fake libvirt, HTTP clients and RPC, so they show what the code sends, defines and answers, not what libvirt, Ceph and the guest do with it.
- Everything below was checked on the lab (three controllers, two compute nodes, Ceph and LVM), with CirrOS guests and test resources that were deleted afterwards, on test packages built from this code and named 1.0.8~rc1 to rc4 (rc4 is the code of this release candidate). The packages went on one node at a time, controllers first; the unit list and states and a hash of `/etc/cloudx` were identical to before on every node, no unit failed, and `vm-default` kept running (the same QEMU process).
  - **Resize.** A server with two NICs, a Ceph and an LVM data volume went from `small` (1 vCPU, 1 GB) to `medium` (2 vCPUs, 2 GB): `ACTIVE` in 9 seconds, the guest restarted (uptime under a minute) with 2 CPUs and about 2 GB, both NICs and all three disks in place, 4/4 pings on each network. The domain XML had `<vcpu>2</vcpu>` and 2097152 KiB for `memory` and `currentMemory`. `revertResize` gave back flavor `small`, 1 vCPU, 1024 MB, and the NICs and disks were unchanged. The guest kept its second CPU after the revert: libvirt answers "failed to find appropriate hotpluggable vcpus" when asked to take one away from a running CirrOS guest, the worker keeps the change in the persistent configuration, and the guest sees it after its next reboot. Memory went down by balloon.
  - **Shelve and unshelve.** The same server: shelve took 3 seconds; both nodes then had no domain, no tap, no instance directory and no iSCSI session, placement showed no allocation for the server, and the volumes stayed `in-use` by the server. Unshelve took 6 seconds on the same node, and about 9 seconds on the other node (comp01 disabled for the test); there the LVM data volume came in over iSCSI. Both NICs and all three disks were back each time, with 4/4 pings on each network.
  - **Live migrate.** The call answered 501 and the server stayed `ACTIVE`.
  - **Server snapshot.** One CirrOS server with a Ceph root volume and one with an LVM (`gp2`) root volume: both calls answered 202; the images were `ACTIVE` after 12 seconds (57 MB) and after about 2 minutes (1.8 GB), and no volume snapshot was left. A new server built from the Ceph image was `ACTIVE`, and a file written in the original server before the snapshot was in it; a server built from the LVM image booted. An upload that image-api refused (409, a name that exists, sent straight to block-store) left the snapshot in `error` with "image-api answered 409".
  - **Delete with snapshots.** One server on Ceph and one on LVM, each with a snapshot of its root volume: after the delete both root volumes were `available` with their snapshots, `rbd snap ls` showed the snapshot, and `lvs` showed the LV and the snapshot. Deleting the snapshots and then the volumes left no image in the Ceph pool and no LV. `DELETE /volumes` answered 409 while a snapshot existed.
  - **Lock.** With a member user, on a locked server: stop, reboot, resize, pause, rebuild, set password, shelve, delete and `volume attach` each answered 409 "server is locked; unlock it first", and a `GET` answered 200. An admin stopped the same locked server. The member user was created for the test and deleted.
- Not tested:
  - Unshelving a server that an older CloudX shelved (the stale-domain case above).
  - `cloudx volume backup` of a Ceph volume. It calls the same export function that had the "File exists" bug.
  - A resize beyond the maximums of a **stopped** server (the redefine path without a restart), except in unit tests.
  - A server snapshot of a server with several data volumes (only the root volume is imaged, as before), and a snapshot taken while the guest writes heavily on LVM.
  - A resize beyond the maximums while the guest has a managed-save image (a suspended server).
  - Several resizes, shelves or snapshots at once on one node.
  - An OVN older than 24.03.8. It is outside the supported platform (see "Known limitations").

## Known limitations

- **Live migration is not built.** It needs qemu over ssh between the nodes, taps and OVN port binding on the target, and a way to move a non-shared LVM disk. It will be built later; until then use cold migration.
- **A server snapshot images the root volume only.** Data volumes are snapshotted and backed up on their own (`docs/snapshot.md`).
- **The image of a server snapshot is as large as the used part of the root volume** (qcow2 of the whole volume, not compressed).
- **OVN version.** As in `docs/releases/v1.0.7.md`: OVN comes from the Ubuntu 24.04 archive; the lab tests ran on 24.03.8 (`noble-updates`). An older OVN is outside what CloudX is tested on.
- The limits of `docs/releases/v1.0.7.md`, `docs/releases/v1.0.6.md` and `docs/releases/v1.0.5.md` still apply.
