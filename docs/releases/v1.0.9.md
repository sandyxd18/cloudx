# CloudX v1.0.9

CloudX 1.0.9 fixes a `stop` that the system undid on its own (7 of 15 stopped servers were running again in the lab), makes a resize wait for the user to confirm or revert it, and adds `cloudx port delete`. It also quiets the load balancer worker on nodes of a cloud that does not run load balancing. The changes are in the compute service, the compute worker, the CLI, the orchestration engine and the lb-worker. There is **one schema change** and **upgrade steps** (below), and several behaviour changes to read first.

## What is new since 1.0.8

**Compute worker**
- **`cloudx server stop` stays stopped.** The worker called `domain.shutdown()`, which only asks the guest to power off, and reported `SHUTOFF` at once. If the power-state loop ran in the seconds before the guest was off, it saw a running domain under a `SHUTOFF` record, set `ACTIVE`, and one pass later auto-recovery found the domain off under an `ACTIVE` record and started it as if it had crashed. In the lab, stopping five CirrOS servers at once left 7 of 15 running again 80 seconds later. Now the worker waits until the domain is off, up to `STOP_SHUTDOWN_WAIT` seconds (60 by default, set in the worker environment), and destroys a guest that ignores the request. The record stays `STOPPING` meanwhile, which the power-state loop leaves alone. The resize path uses the same helper with its own wait (`RESIZE_SHUTDOWN_WAIT`, 30 seconds). A relocated server that has to end `SHUTOFF` is stopped by the same function.
- A resize now ends in `VERIFY_RESIZE`, and a revert ends in the status the server had before (see below).

**Compute API**
- **A resized server waits in `VERIFY_RESIZE`** until `confirmResize` or `revertResize`, as in Nova. Before, it went straight to `ACTIVE` with its rollback snapshot still in the record, so a second resize silently replaced the size to go back to. `resize` is accepted from `ACTIVE` or `SHUTOFF` (409 otherwise, and 409 from `VERIFY_RESIZE` until the resize is confirmed or reverted). `confirmResize` needs `VERIFY_RESIZE`, or an `ACTIVE` server that 1.0.8 left with its snapshot. `revertResize` works from `VERIFY_RESIZE`, from `ERROR` (what a failed resize leaves) and from such an `ACTIVE` server.
- **A stopped server stays stopped through a resize.** The worker and `confirmResize` set `ACTIVE` whatever the server was before; for a stopped server the power-state loop then found a stopped domain under an `ACTIVE` record and auto-recovery started it. The compute record now keeps the status from before the resize (`original_status`), and confirm and revert restore it.

**CLI**
- `cloudx server confirm-resize REF` and `cloudx server revert-resize REF` are new; `cloudx server resize` tells the user about them. Without them a CLI user had no way out of `VERIFY_RESIZE`.
- `cloudx port delete REF` deletes a port. A port that a server still uses is refused with a pointer to `cloudx server port remove`; `--force` deletes it anyway. The command reads the servers' `port_id` and `extra_port_ids`, because `server port add --network` makes a port with no `device_id` and the compute API does not set one when it attaches the port. A port with a `device_owner` (a router interface, for example) is refused too. The API is unchanged. (1.0.9-rc1 checked only `device_id` and deleted a port that had just been added to a running server; this is fixed in 1.0.9.)

**Orchestration**
- A stack update that changes a server's flavor confirms the resize itself: the template is the decision, and nobody else would confirm it.

**Dashboard**
- Confirm and revert resize are enabled in `VERIFY_RESIZE` only (they were also enabled in `RESIZE`, where the API now answers 409).

**lb-worker**
- A poll of load-balancer-api that fails is logged once, again every 5 minutes while it keeps failing, and the recovery is logged. A compute node of a cloud without load-balancer-api logged the same warning every 5 seconds (720 times an hour). Every failure is still logged at debug level.

## Behaviour changes to read first

1. **A resize waits for a decision.** A server is in `VERIFY_RESIZE` after a resize, with the new size already in the guest. A script that resizes and then uses the server must wait for `VERIFY_RESIZE` and may confirm at once (`cloudx server confirm-resize`). A server stays in `VERIFY_RESIZE` until someone does; there is no automatic confirm.
2. **`resize` refuses states it used to accept.** Only `ACTIVE` and `SHUTOFF` servers can be resized. A server in `VERIFY_RESIZE`, `RESIZE`, `BUILD`, `ERROR`, `SHELVED_OFFLOADED` or any other state gets 409. Before, the API accepted any state and overwrote the rollback snapshot.
3. **`stop` takes as long as the guest takes to power off.** The call returns at once (status `STOPPING`), but the compute worker handles one request at a time, so another request for the same node can wait behind a stop for up to 60 seconds. A guest that has not powered off after 60 seconds is destroyed, a hard power-off. A guest that never answers ACPI used to stay running with a `SHUTOFF` record until the next sync flipped it back; now it is stopped.
4. **Schema change.** `compute_servers.original_status` (migration `compute_0004`). Run `cloudx-manage db sync` (see below). This was "no schema change" in 1.0.7 and 1.0.8.

## Upgrading

Order: the controllers first (compute API, orchestration), then the compute nodes (compute worker, lb-worker). Every node must have all of its CloudX packages at one version. Running VMs are not stopped: QEMU does not run under a CloudX unit.

### From 1.0.8 `.deb` packages

1. Download the packages of the release and check them (`docs/deb-install.md` section 3, "Downloading a release").
2. On each node, list what is installed and install the new version of exactly those packages in one command. `--force-confold` keeps your configuration files:

   ```bash
   dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'cloudx-*' | awk '$1 ~ /^ii/ {print $2}'
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-common_*.deb ./cloudx-<each package from the list>_*.deb
   ```

   The package scripts restart the units that were active and leave disabled units disabled.
3. Right after the packages are installed on the first controller (the one with `cloudx-db`), apply the schema change:

   ```bash
   sudo cloudx-manage db sync
   ```

   It is safe to run again. Until it has run, a compute API of 1.0.9 selects a column that the table does not have, so requests that read servers fail; the window is the time between the package install and this command, so run it at once.
4. No catalog sync is needed. `systemctl list-units --failed 'cloudx-*'` must list nothing. Check that the version took: `dpkg-query -W cloudx-common` on each node.

During the upgrade, between the first controller and the last compute node, do not resize or revert a server:

- A new compute API with an old compute worker leaves the server `ACTIVE` after a resize (the old worker sets that), with the snapshot in the record; `confirmResize` and `revertResize` accept that state.
- An old compute API with a new compute worker leaves the server in `VERIFY_RESIZE` after a revert too, because the old API does not tell the worker that it is a revert; `confirmResize` then clears it.

These mixed-version cases come from reading the code; they were not tried.

A server that is in `RESIZE` when the upgrade starts finishes as before. A server that 1.0.8 left `ACTIVE` after a resize still has its snapshot: `confirmResize` closes it and `revertResize` goes back, as in 1.0.8.

From 1.0.7 or older, do the earlier upgrades first (`docs/releases/v1.0.8.md`, `docs/releases/v1.0.7.md`).

## What was tested, and what was not

- The unit tests pass on the changed code, and CI builds every package. Each change was written test first and watched fail for the right reason. They run against fake libvirt, HTTP clients and RPC, so they show what the code sends, defines and answers, not what libvirt and the guest do with it.
- Everything below was checked on the lab (three controllers, two compute nodes, Ceph and LVM) on test packages named 1.0.9~rc0, rc0.1 and rc0.2 (rc0.2 is the code of this release candidate), with CirrOS guests and test resources that were deleted afterwards. The migration was applied with `cloudx-manage db sync` on the first controller.
  - **Resize with confirmation.** A server went from `small` to `medium`: `VERIFY_RESIZE` after 21 seconds, with the new size in the flavor fields; a second resize answered 409; `confirm-resize` gave `ACTIVE`; a second confirm answered 409. A resize followed by `revert-resize` gave back the old flavor and `ACTIVE`; a revert with nothing to revert answered 409.
  - **Stopped server, resize beyond the domain limit** (2 vCPUs and 2 GB to 4 vCPUs and 3 GB): `VERIFY_RESIZE`, the inactive domain XML had the new limits and the domain stayed shut off; after a start the guest had 4 CPUs. This covers the case 1.0.8 listed as not tested.
  - **A stopped server stays stopped.** `confirm-resize` on that server gave `SHUTOFF` and the domain was still off 75 seconds later (two sync passes); `revert-resize` from a stopped server also ended `SHUTOFF`.
  - **The stop race.** Five CirrOS servers on two compute nodes were stopped at once, three times; 80 seconds after each stop 7 of the 15 were running again on the 1.0.9~rc0.1 build and 0 of 15 on 1.0.9~rc0.2. The `stop` calls took 6 to 10 seconds in both runs.
  - **lb-worker.** On a compute node without load-balancer-api the worker logged 4 "still failing" lines in 20 minutes instead of one line every 5 seconds.
- **1.0.9-rc1 was installed on the lab** from the release `.deb` files (three controllers, two compute nodes, controllers first, over the test packages; the checksums of the 48 files matched `SHA256SUMS`; `cloudx-manage db sync` after the first controller, no error): all packages at 1.0.9~rc1-1, no unit failed, the unit list and states and a hash of `/etc/cloudx` were identical to before on every node, no traceback in the logs of the compute, block-store and image services and workers, and `vm-default` kept running (the same QEMU process). Checked again with CirrOS servers, deleted afterwards:
  - A server went from `small` to `medium`: `VERIFY_RESIZE` after 21 seconds; a second resize answered 409; `confirm-resize` gave `ACTIVE`. A resize followed by `revert-resize` went back to the flavor the server had before that resize, `ACTIVE`.
  - Five servers stopped at once, twice: 0 of 10 were running again 80 seconds later (the `stop` calls took 9 and 10 seconds).
  - A stopped server was resized and confirmed: `VERIFY_RESIZE`, then `SHUTOFF` after the confirm, and still `SHUTOFF` 75 seconds later.
  - `cloudx port delete` of a port added to a running server with `server port add --network` was **deleted** by rc1 and then `server port remove` answered 404: the bug fixed in 1.0.9.
  - The fixed `cloudx port delete` (the CLI of the 1.0.9 code, run from a temporary directory on a controller, nothing installed): the extra port and the primary port of a running server were refused; after `server port remove` the delete worked and the port was gone.
- Not tested:
  - The 1.0.9 release files themselves on the lab; the final install of the packages is checked after the tag, and `cloudx port delete` was tried with the CLI of the code, not the installed package.
  - A stack update that changes a server's flavor (unit test only).
  - Upgrading a lab that has a server in `RESIZE` or one that 1.0.8 left `ACTIVE` with a snapshot.
  - The mixed-version cases above.
  - A `stop` of a guest that ignores ACPI (the destroy after 60 seconds is covered by a unit test).
  - A stop of a guest that takes a long time to power off while other requests for the same node wait.
  - An OVN older than 24.03.8. It is outside the supported platform (see "Known limitations").

## Known limitations

- **Live migration is not built** (`POST /servers/{ref}/live-migrate` answers 501). Use cold migration.
- **No automatic confirm of a resize.** A server waits in `VERIFY_RESIZE` until someone confirms or reverts.
- **A server snapshot images the root volume only,** as in 1.0.8.
- **OVN version.** As in `docs/releases/v1.0.7.md`: OVN comes from the Ubuntu 24.04 archive; the lab tests ran on 24.03.8 (`noble-updates`). An older OVN is outside what CloudX is tested on.
- The limits of `docs/releases/v1.0.8.md`, `docs/releases/v1.0.7.md` and `docs/releases/v1.0.6.md` still apply.
