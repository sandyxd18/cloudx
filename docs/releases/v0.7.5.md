# CloudX v0.7.5

Makes telemetry, billing and events actually work end to end, and fixes the dashboard pages that sat on top of them.
There are **upgrade steps** (see below).

## Upgrading from v0.7.0

1. **Migrate the event database** before restarting event-api: `sudo make migrate` (adds `next_retry_at` and
   `last_error` to webhook deliveries, idempotent).
2. **Install the three new worker units** from `etc/systemd/`: `cloudx-billing-worker` and `cloudx-event-worker` on the
   controller, `cloudx-telemetry-worker` on the compute node (it needs libvirt and a copy of `/etc/cloudx/cloudx.env`).
   Workers need `AUTH_ADMIN_PASSWORD` from that file. They never ran as services before.
3. **New environment variables** (all optional): `CORS_ORIGINS` (default `http://localhost`; `*` is ignored),
   `EVENT_ALLOW_PRIVATE_WEBHOOKS` (default off; webhooks to private/loopback addresses are rejected),
   `TELEMETRY_RETENTION_DAYS` (default 7).
4. **Behaviour changes:** non-admin users only see their own project in telemetry, billing and events; metric ingest,
   usage records, rating sheets and invoice creation for other projects are admin only; a webhook secret is shown only
   when the subscription is created; `POST /billing/invoices` takes `year`/`month` as query parameters and returns 409
   when the invoice already exists.

## Telemetry
- CPU percent is computed from the `cpu_time` delta; disk and network are per-second rates, not raw counters.
- New `GET /telemetry/series` (time-bucketed), `stats` takes `hours` and returns `min/max/last`, lists accept
  `limit/offset/since/until`. Old samples are cleaned hourly.

## Billing
- New admin endpoints `POST /billing/usage-records/batch` and `POST /billing/cleanup`; the worker was calling both
  before they existed, so no usage was ever recorded. Costs are computed on the server from rating sheets.
- The worker bills only the hours a resource existed, includes load balancers, and uses one unit (`hour`).
- Invoices honour `year`/`month`, are created in one transaction, and the summary has a per-resource breakdown.

## Events
- Events published to the RabbitMQ fanout exchange are now stored by event-api and matched to webhooks.
  Compute, conductor and networking publish lifecycle events with `project_id` (server create/end/delete/resize/crash,
  volume create/attach/detach/delete, floating IP, router).
- The event worker delivers with an HMAC signature and exponential backoff, and updates delivery status
  (`pending`, `success`, `failed`); failures are visible with `last_error` and `next_retry_at`.

## Dashboard
- Telemetry uses the Cloudscape `LineChart` with a time range; Billing shows correct totals, real PDF download,
  invoice detail, usage records and admin invoice creation; Events has a payload viewer, webhook management and
  deliveries with retry. Plus quick-create modals and launch form fixes.

## Networking
- A router's external port keeps its own address and the default route goes through the upstream gateway.

## CLI
- `billing invoice-show`, `billing rating-sheet-show`, `billing rating-sheet-update`; `invoice-create --year --month`.

## Known limitations
- Resources deleted in the middle of an hour are not billed for that interval (the APIs do not return `deleted_at`).
- Prometheus `/metrics` is unauthenticated; billing-api still allows CORS `*`.
- Events without a `project_id` are admin-visible only and do not trigger webhooks.
- The `load_balancer` rating (750 IDR/hour) is a placeholder.
