# CloudX v1.0.6

CloudX 1.0.6 closes one known limitation of 1.0.5: `cloudx server create` takes `--network` more than once, so a server with several NICs no longer needs the API. The change is in the CLI only. There is no schema change, no new service, and no change in the API or in the services. There are **upgrade steps** (below), and one behaviour change to read first.

## What is new since 1.0.5

**Compute (CLI)**
- `cloudx server create` takes `--network` more than once. The first one is the primary network (`network` in the API, the `port_id` port); every other one adds a NIC on that network (`networks` in the API, stored in `extra_port_ids`):

  ```bash
  cloudx server create web-1 --image ubuntu --flavor small --network app-net --network db-net
  ```

  The API has taken `networks` since 1.0.2. The CLI sent one network only, and a second `--network` was dropped without a word (the last value won).
- A network given twice is refused (`network app-net is given twice; each --network adds one NIC on a different network`) before anything is sent: the API drops a repeated network silently, so the server would have fewer NICs than asked for.
- With one `--network` the request is the same as before (no `networks` key). `--ipv6` applies to every network, and the request is refused if one of them has no IPv6 subnet. `--security-group` applies to every port of the server.

**Documentation**
- `docs/multi-network.md` has an "At creation" section, and `docs/user-guide-cli.md` an example.
- After 1.0.5 was tagged, the lab showed that a security group with no ICMPv6 ingress rule does **not** stop the router advertisements. `docs/ipam.md`, `docs/feature-comparison.md` and `docs/releases/v1.0.3.md` said the opposite and are corrected. The lab results are in `docs/releases/v1.0.5.md` (Ubuntu guest, `dhcpv6-stateful`, a security group) and `docs/releases/v1.0.4.md` (evacuation of a one-NIC server).

## Behaviour changes to read first

1. **A second `--network` is no longer ignored.** A script that passed `--network` twice (by mistake or on purpose, relying on the last one winning) now gets a server with one NIC per network, or an error if a network is repeated. Nothing else in the command changed.

## Upgrading

Only `cloudx-cli` has a code change. The services behave as in 1.0.5, so nothing has to be restarted for this feature.

### From 1.0.5 `.deb` packages

1. Download the packages of the release and check them (`docs/deb-install.md` section 3, "Downloading a release").
2. On each machine that has the CLI, install the new `cloudx-cli`:

   ```bash
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-cli_*.deb
   ```

3. A node that should stay at one version for all of its CloudX packages (the rule of the earlier releases) takes the full upgrade of `docs/releases/v1.0.5.md`, "Upgrading", with the 1.0.6 packages. No `cloudx-manage db sync` and no catalog sync are needed.
4. Check: `dpkg-query -W cloudx-cli`; `cloudx server create --help` shows `--network` with "repeat it for more NICs".

From 1.0.4 or older, do the earlier upgrades first (`docs/releases/v1.0.5.md`, `docs/releases/v1.0.4.md`).

## What was tested, and what was not

- The unit and packaging tests pass on the changed code, and CI builds every package. `tests/cli/test_server_create.py` has six tests for this change: the primary network and the extra ones in the payload, the order of three networks, one network leaving the payload as before (no `networks` key), a repeated network refused with nothing sent, `--network` still required, and `--ipv6` together with several networks. They run the CLI against a fake HTTP client, so they show what the CLI sends, not what the API and the compute worker do with it.
- **1.0.6~rc1 was installed on the lab** (three controllers, two compute nodes, one node at a time from the release `.deb` files; the checksums of all 48 files matched `SHA256SUMS`): all packages at 1.0.6~rc1-1, no unit failed, the unit list and states and a hash of `/etc/cloudx` were identical to before on every node, and `vm-default` kept running (the same QEMU process). Checked with the `cloudx-cli` package installed on a controller, with test resources that were deleted afterwards:
  - **A repeated network is refused**: `--network a --network a` printed `network a is given twice; each --network adds one NIC on a different network`, exited with status 2, and no server was created.
  - **Two networks give two NICs**: `--network a --network b` gave a server `ACTIVE` with `port_id` and `extra_port_ids` set, two interfaces in the libvirt domain with the MACs of the two ports, two taps in Open vSwitch with `ovn-installed="true"`, and both logical switch ports `up` and bound to the same chassis. Inside a CirrOS guest `eth0` and `eth1` each had the address of its port and a route for its subnet.
  - **Evacuation of that server** with the source host alive (`forced_down` set on it, as in the one-NIC test of `docs/releases/v1.0.4.md`): the server was `ACTIVE` on the other compute node in 17 s. About 29 s after the start the compute worker of the source destroyed the stale domain and ran `ovs-vsctl del-port` for **both** taps; the source was left with no domain of the server and no tap of it. `Claiming` lines in `ovn-controller.log` rose by 28 on the new host and 24 on the source (twice the 14 and 12 of the one-NIC test), the last of them in the second the taps were deleted, and none followed in the next 60 s. Both ports were bound to the new host's chassis and `up`.
  - **Traffic on both NICs**: a CirrOS client on each network pinged its address of the server, 4/4 before the evacuation and 8/8 after it, with no loss (the client of the first network on the source host, so across hosts; the client of the second network on the new host).
- Not tested: rebuild of a server made before 1.0.4, a port made before the 1.0.4 upgrade, a dual-stack port on a `slaac` subnet, and an OVN older than 24.03.8 (see `docs/releases/v1.0.5.md`).

## Known limitations

- `server create` takes network names only: each NIC gets an address from its network, in the order of `--network`. To control more than that, create the port first and attach it with `server add-port` (`docs/multi-network.md`, "After creation").
- The limits of `docs/releases/v1.0.5.md` (one DNS server in the router advertisement, a subnet cannot be edited) and those in `docs/quickstart.md` ("Known limitations") and `docs/deb-install.md` section 8 still apply.
