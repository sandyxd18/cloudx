# CloudX v1.0.0

> **Draft for 1.0.0-rc1.** `VERSION` is `1.0.0-rc1`; the tag is not pushed yet. This page is finished at the tag of 1.0.0. Anything marked *(rc)* is to be re-checked on the release candidate.

CloudX 1.0.0 is the first release that is installed from `.deb` packages, with documentation and tutorials for a first-time user. The services are the ones of 0.8.6 plus Messaging and Reservation. There are **upgrade steps**.

## What is new since 0.8.6

**Installation and operation**
- 47 `.deb` packages for Ubuntu 24.04 amd64, built from `packaging/manifest.toml`: `cloudx-common`, `cloudx-db`, one package per API or daemon, role packages `cloudx-controller`, `cloudx-compute`, `cloudx-storage`, and a standalone `cloudx-cli`. The release page carries every package, the release tarball and `SHA256SUMS`; there is no apt repository (`apt install ./file.deb` is the install path).
- Twenty stateless APIs sit behind nginx on unix sockets; the external ports are the same as before. `object-store-api`, `metadata-api`, `metadata-proxy` and `dashboard` keep their own TCP listener because they depend on the client IP.
- A service catalog in auth: services, workers, host daemons and the CLI resolve their peers through it. `/etc/cloudx/cloudx.conf` needs only `auth_api_url`; a `<name>_api_url` key still overrides the catalog. `cloudx-manage catalog sync` fills it.
- `cloudx-manage db sync` (with `cloudx-db-migrate` kept as an alias) and `cloudx-manage conf init`. Host preparation scripts ship with the role packages: `cloudx-setup-compute`, `cloudx-setup-storage`, `cloudx-setup-ceph-secret`.
- Pre-release builds use the Debian version `1.0.0~rc1-1`, so `apt` sees rc1 as older than 1.0.0. On the release page the `~` in a pre-release file name is shown as `.`; `SHA256SUMS` uses the names as published.
- MIT license, `CHANGELOG.md`, `SECURITY.md`, `CONTRIBUTING.md`. CI builds every package and checks it with `dpkg-deb` and lintian (`scripts/check-debs.sh`).

**New services**
- Messaging (Zaqar-like, port 8022): per-project queues with post, peek, claim and delete, at-least-once delivery (`cloudx queue ...`, Queues page). Limits: 64 KiB body, 10,000 messages per queue, message ttl 60 s to 14 days.
- Reservation (Blazar-like, port 8023): time-boxed flavor leases (`cloudx reservation ...`, Reservations page). A lease is refused (409) when overlapping leases of all projects would exceed the cluster's VCPU or RAM from Placement (503 when Placement has no inventory).

**Documentation**
- English throughout. A quickstart for one machine, `SETUP.md`, the package reference `docs/deb-install.md`, an architecture page with the service and port table, a CLI guide whose commands are checked by a test, and tutorials: a three-node cloud, auto-scaling, Ceph, Kubernetes and a dashboard tour. The tarball install moved to `docs/tarball-install.md` (legacy).

**Fixes**
- A clean `.deb` install now boots a VM: stale OVN chassis cleanup, `ovn-bridge-mappings`, block storage preparation.
- Router gateways land on a real gateway chassis; the node's OVN system-id survives an Open vSwitch restart.
- Deleting a security group removes its OVN port group and ACLs; rule ports set from the CLI are kept.
- RBD volumes boot and attach against a real cephx cluster (Ceph 19.2.3 clients).
- The RabbitMQ password is no longer written to logs; RPC connections use TCP keepalive, so a dead peer is noticed in about a minute after a controller crash.
- A server deleted while it is in BUILD no longer leaves a running domain; tap devices are recreated before a domain starts after a host reboot.
- Anti-affinity: a server group no longer accepts a member when every node already holds one (it answers 409 `No valid host`).
- `cloudx scaling-group scale-out/scale-in` and stack operations no longer answer 401 with the CLI (`X-Auth-Token` is accepted when the caller's credentials are forwarded).
- The telemetry worker sends metrics: without this there was no CPU, memory, disk or network data, and CPU-based auto-scaling, alarms and rollups had nothing to work with.
- ha-watchdog falls back to the last ha-api URL that resolved when the catalog is down; `cloudx flavor list` shows memory and disk; node configuration files are `640 root:cloudx`.
- `cloudx ha protect` and `unprotect` accept a server name, as the CLI sends it.
- A missing load balancer API no longer stops the DNS worker's sweep of automatic names.
- Subnets created without a nameserver no longer hand VMs the lab's resolver address (`172.20.0.118`) when the DNS service is not installed: they get `dns_upstream` (`1.1.1.1`, `8.8.8.8` by default). `cloudx.conf.sample` ships `dns_public_address` and `dns_resolver_address` commented out; a `cloudx.conf` that already sets them keeps working.

**Removed**
- Leftovers of the Docker Compose era and one-off scripts that nothing used: the container entrypoints and reference configs under `services/` (`ovn`, `postgres`, `rabbitmq`, `haproxy`, `keepalived`, `backup`, `certs`, `grafana`, `prometheus`), `make generate-certs`, `.env.example`, `scripts/bootstrap.sh`, the standalone `cli/compute`, `cli/image`, `cli/networking` and `cli/block-store` scripts (the `cloudx` command replaces them), and the design notes under `docs/superpowers/`. Nothing in the packages or the tarball scripts depended on them.

## Upgrading

Order: the controller first, then the other nodes. Mixing 0.8.6 and 1.0.0 packages across nodes works, but every node must have all of its CloudX packages at one version, because each package depends on `cloudx-common` of exactly the same version.

### From 0.8.6 `.deb` packages

Tested on 2026-10-26 on one compute and storage node (11 packages: `cloudx-common`, the `cloudx-compute` and `cloudx-storage` role packages and their services) with a build of `1.0.0~rc1-1`. *(rc: repeat with the release candidate.)*

1. Download the packages of the release and check them: `sha256sum -c SHA256SUMS --ignore-missing`.
2. On each node, list what is installed and install the new version of exactly those packages in one command. `--force-confold` keeps your configuration files:

   ```bash
   dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'cloudx-*' | awk '$1 ~ /^ii/ {print $2}'
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-common_*.deb ./cloudx-<each package from the list>_*.deb
   ```

   The package scripts restart the units that were active and leave disabled units disabled.
3. On the controller, once: `sudo cloudx-manage db sync`. New tables in this release: `messaging` and `reservation`.
4. On the controller: `sudo cloudx-manage catalog sync --dry-run`, read it, then `sudo cloudx-manage catalog sync`. `systemctl list-units --failed 'cloudx-*'` must list nothing.
5. Optional new services: install `cloudx-messaging-api` and `cloudx-reservation-api` on the controller, run steps 3 and 4 again, and add `messaging_api_url` and `reservation_api_url` to `/etc/cloudx/auth-api/auth-api.conf` if they run on another node than auth.

What the rehearsal showed on the compute and storage node: the set of active units, every file under `/etc/cloudx`, the five secrets and the libvirt binding were identical before and after; units that were disabled stayed disabled; a VM scheduled to the upgraded node afterwards booted, and a volume attached to it. A rollback to 0.8.6 (`sudo apt install --allow-downgrades -o Dpkg::Options::=--force-confold` with the old packages of the same list) gave the same state as before the upgrade. Running VMs are not touched: their QEMU processes do not belong to a CloudX unit.

Not rehearsed: the controller's own upgrade order beyond `db sync` and `catalog sync`, and an upgrade with a VM on the node being upgraded. *(rc)*

### From the 0.8.x tarball

Follow `docs/deb-install.md` section 7 (stop and remove the old units, move `/opt/cloudx` aside, install the packages, check nginx, fix the catalog). Then continue with steps 3 to 5 above. `*_api_url` keys left in your old `cloudx.conf` keep working as overrides of the catalog; remove them once `catalog sync` shows the right addresses.

### Changes to know about

- Configuration files are conffiles. If a package ships a different default than the file on disk and you changed it, `dpkg` asks; `--force-confold` keeps yours.
- Per-service configuration files of some packages (for example `conductor`, `event-api`, `billing-api`, `orchestration-api`, `key-manager-api`, `k8s-engine-api`) ship their own `database_url` with the default password `cloudx`. If you changed the PostgreSQL password, change it in those files too (`docs/deb-install.md` section 6.5).
- `docs/releases/` notes for 0.8.6 and older describe tarball steps.

## Known limitations

The full lists are in the documents of each service; the ones that matter most when you start:

- Ubuntu 24.04 amd64 only. Python 3.12 environments are bundled in the packages.
- No TLS between services or on the nginx front. PostgreSQL, RabbitMQ and OVN central are single instances; HAProxy/keepalived, replication, a PostgreSQL backup job and Prometheus/Grafana are not provided (`docs/production-readiness.md`).
- Instance HA recovers VMs when a compute node dies (with the watchdog), but it is not power fencing and not controller HA (`docs/ha.md`).
- Block storage needs a backend before the first VM: every VM has a root volume. LVM with iSCSI is the tested path; Ceph RBD was tested on a six-node lab and not on the current hardware.
- Reservation does not yet reserve capacity from compute; leases are a ledger. Messaging is a basic queue on PostgreSQL.
- An auto-scaling group starts empty (`--min-instances` is only the floor for scale-in), and deleting a group leaves its VMs.
- `cloudx server create` has no server group option; use the API field `server_group`.
- The Hypervisors list (CLI and dashboard) shows `0` running VMs and no CPU or memory usage: nothing feeds those columns of the placement heartbeat yet.
- The metadata service for VMs on compute nodes needs `scripts/setup-metadata-route.sh` (single host); configuration drive delivery works everywhere.
- The four services with their own TCP listener trust the client IP they see; a trusted-proxy model for them is future work.
