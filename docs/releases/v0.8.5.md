# CloudX v0.8.5

Four new services: File Store (Manila-like), Container (Zun-like), Database (Trove-like) and Instance HA (Masakari-like). All are "not 1:1" with their OpenStack counterparts. There are **upgrade steps**.

## Upgrading from v0.8.0
1. Deploy `services/` to every node, run `scripts/install-systemd.sh` and `cloudx-db-migrate` for `file_store`, `container`, `database` and `ha` (from `/tmp`).
2. Add to `/etc/cloudx/cloudx.conf`: `file_store_api_url`, `file_store_host`, `file_store_mount_root`, `container_api_url`, `database_api_url`, `database_public_url` (must be reachable from tenant VMs) and `ha_api_url`. Append with a leading newline; the file may not end with one.
3. Controller: enable `cloudx-file-store-api`, `cloudx-container-api`, `cloudx-database-api`, `cloudx-ha-api`. Storage node: `cloudx-file-store-worker` (create its conf with `file_store_api_url` and `file_store_host`). Container nodes: set `container_host` in `container-worker.conf` (needs a `[DEFAULT]` header) and enable `cloudx-container-worker` (the installer adds Docker with `iptables:false`, `bridge:none`).
4. Every compute node: set `ha_api_url` to the controller (`http://<controller>:8020`), then redeploy `compute-worker` and `block-store`.
5. Rebuild the dashboard.

## Changes
- **File Store** (`file-store-api` :8017, CLI `cloudx file-store`): share networks, shares (LV + ext4, online extend), access rules (`rw`/`ro`, per IP or CIDR). NFSv4 only through NFS-Ganesha, one process per share network, no NAT. No rule means deny all; wide ranges are rejected; root is squashed.
- **Container** (`container-api` :8018, CLI `cloudx container`): Docker with `--network none` and an OVN port per container, so security groups apply. Create, start, stop, restart, logs, delete. Hardened by default (dropped capabilities, `no-new-privileges`, pids limit, mandatory CPU and memory limits, no host mounts).
- **Database** (`database-api` :8019, CLI `cloudx database`): PostgreSQL and MariaDB on a VM (local, block or file storage) or in a container (local volume). Per-instance security group limited to `allowed_cidr`; random admin password returned once and not stored; VM readiness through a one-time cloud-init callback.
- **Instance HA** (`ha-api` :8020, CLI `cloudx ha`): compute workers send a heartbeat every 10 s; a host silent for 60 s and still silent 30 s later is declared dead. Fixed order: `forced_down`, revoke the node's iSCSI ACLs (new block-store `POST /internal/fence`), then evacuate. Only protected servers are evacuated; each is checked to reach `ACTIVE` within 300 s and logged in `/recoveries`. Servers with a volume on the failed host are skipped, and protecting them is refused.
- `PUT /os-services/{host}` and `POST /servers/{id}/evacuate` now also accept the internal token.
- Container worker: `data_path` volumes, `docker rm -v`, logs include stderr.
- Dashboard pages: File Store, Containers, Databases, High availability.

## Known limitations
- **File Store**: no snapshots, clones, shrink, quotas, SMB/CIFS, replication, NFSv3 or Kerberos; one worker node; share root is mode 0777 and access relies on IP rules and root squash; restarting Ganesha starts a 10 s NFSv4 grace period.
- **Container**: no exec, block volumes, published ports or floating IPs, image build, private registries, restart policy, resize or console; images are pulled by the node from public registries; the network is attached within about 5 s of start; scheduling is "fewest containers"; no quota.
- **Database**: no backup and restore, in-instance database and user management, replication, resize, upgrade or parameter groups; container with block or file storage not supported. PostgreSQL on file (NFS) is rejected (it failed in the lab, probably root squash); MariaDB on NFS works but is not recommended. The admin password sits in cloud-init user-data (VM) or the container environment. Container data is lost if the node is lost. Start/stop of a VM instance only changes the recorded status. Create containers one at a time: concurrent creation can hit a duplicate-IP race in networking-api (pre-existing). An interrupted create or delete leaves an `error` row; delete it again.
- **Instance HA**: host monitor only (no process or VM monitors). No power fencing: a hung node may keep running its VMs; it is only blocked from writing through iSCSI, and its old VMs must be cleaned up by hand before the host returns. Servers with a volume on the failed host are not recovered. Node recovery is manual (`forced_down=false`, then `cloudx ha reset HOST`). No evacuation priority. A host that never reported an iSCSI initiator name cannot be fenced and is never auto-evacuated. After an ha-api restart every host gets a fresh 60 s before it is judged. Fencing was verified against the lab's targetcli: removing the ACL closed the open session.
- Verified in the lab with Ubuntu 24.04 guests (and CirrOS for HA); CirrOS has no NFSv4 client and does not run user-data.
