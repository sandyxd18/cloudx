# CloudX v1.0.5

CloudX 1.0.5 closes two of the known limitations of 1.0.4, both on IPv6 subnets behind a router: `cloudx router add-interface` on a subnet that has no gateway now answers 400 instead of 502, and the router advertisements now name a DNS server (RDNSS). There is no schema change and no new service. There are **upgrade steps** (below), and two behaviour changes to read first.

## What is new since 1.0.4

**Networking**
- `cloudx router add-interface` on a subnet that has no `gateway_ip` is refused with HTTP 400 before anything reaches OVN or the database. An IPv6 subnet may be created without a gateway, but a router port takes its address from it: the address came out as `/64`, `ovn-nbctl` refused it (`invalid network address: /64`) and the API answered 502. The message says to create the subnet again with `--gateway`, because a subnet cannot be edited.
- The router advertisements of a router port on an IPv6 subnet carry a DNS server (RDNSS, RFC 8106): the first IPv6 address in the subnet's `--dns`. It is `ipv6_ra_configs:rdnss` on the logical router port. Router ports that already exist get it when `cloudx-networking-api` starts, like the rest of the advertisement. Setting it is best effort, as before: if OVN refuses, the error is logged and the interface is kept.
  - OVN takes **one** RDNSS server per router port (ovn-nb(5)), so a second IPv6 server in `--dns` is not advertised, and an IPv4 server never is.
  - IPv6 subnets have **no default DNS** (the default applies to IPv4 only), so a subnet advertises a server only if it was created with an IPv6 `--dns`.
  - It matters most on a `slaac` subnet, where a guest without cloud-init has nothing else to learn a resolver from. On `dhcpv6-stateless` and `dhcpv6-stateful` subnets DNS also comes in the DHCPv6 reply, and a cloud-init guest gets it from `network-config`.

**Documentation**
- `docs/ipam.md` describes the RDNSS and the gateway rule of `router add-interface`.

## Behaviour changes to read first

1. **`router add-interface` on a subnet with no gateway is a 400, not a 502.** Nothing that worked before stops working: the 502 left no interface behind. A script that tested for 502 should test for 400. Subnets cannot be edited, so such a subnet has to be made again with `--gateway`.
2. **A guest that honours RDNSS will start using the advertised server.** This applies to a router port on an IPv6 subnet that has an IPv6 `--dns`, once the port is advertising it (new ports at once, existing ones after `cloudx-networking-api` restarts). Many guests (systemd-networkd, NetworkManager) add it as a resolver; a guest may then have the server from the advertisement as well as the one from `network-config` or DHCPv6.

## Upgrading

Order: the controller first, then the compute nodes. Every node must have all of its CloudX packages at one version. The code change is in `cloudx-networking-api` (controller), but every package takes the new version.

### From 1.0.4 `.deb` packages

1. Download the packages of the release and check them (`docs/deb-install.md` section 3, "Downloading a release").
2. On each node, list what is installed and install the new version of exactly those packages in one command. `--force-confold` keeps your configuration files:

   ```bash
   dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'cloudx-*' | awk '$1 ~ /^ii/ {print $2}'
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-common_*.deb ./cloudx-<each package from the list>_*.deb
   ```

   The package scripts restart the units that were active and leave disabled units disabled. Running VMs are not stopped: QEMU does not run under a CloudX unit.
3. No `cloudx-manage db sync` and no catalog sync are needed. Running them does no harm.
4. `systemctl list-units --failed 'cloudx-*'` must list nothing. Check that the version took: `dpkg-query -W cloudx-common` on each node.
5. The restart of `cloudx-networking-api` sets the RDNSS on the router ports of IPv6 subnets that have an IPv6 DNS server. Check one: `sudo ovn-nbctl get logical_router_port lrp-<router>-<subnet> ipv6_ra_configs`.

From 1.0.3 or older, do the earlier upgrades first (`docs/releases/v1.0.4.md`, `docs/releases/v1.0.3.md`).

## What was tested, and what was not

- The unit and packaging tests pass on the changed code, and CI builds every package. The changes have their own tests: `tests/networking/test_ipv6_router_interface_gateway.py` (a subnet with no gateway is refused with 400, nothing reaches OVN or the database before the refusal, a subnet with a gateway still gets its interface) and `tests/networking/test_ipv6_router_advertisements.py` (the first IPv6 server is advertised and an IPv4 one skipped, none without an IPv6 server, the RDNSS is set again when `cloudx-networking-api` starts). They ran against a fake `ovn-nbctl`, so they show what CloudX asks OVN to set, not what OVN does with it.
- **1.0.5~rc1 was installed on the lab** (three controllers, two compute nodes, one node at a time from the release `.deb` files; OVN 24.03.8): all packages at 1.0.5~rc1-1, no unit failed, the unit list and states and a hash of `/etc/cloudx` were identical to before on every node, and `vm-default` kept running (the same QEMU process). Checked on it, with test resources that were deleted afterwards:
  - **`cloudx router add-interface` on an IPv6 subnet created without a gateway** answered 400 with the new message (it was 502 on 1.0.4), and no router port was left in OVN.
  - **RDNSS in the database**: on a subnet created with the DNS servers `10.0.0.53`, `2001:db8::53` and `2001:db8::54`, the router port had `rdnss="2001:db8::53"` (the first IPv6 server; the IPv4 one is skipped and the second IPv6 one is not sent). A subnet with no DNS had no `rdnss`.
  - **RDNSS on the wire**: `tcpdump` on the tap of a CirrOS server on a `slaac` subnet, after a reboot of the server, showed the router advertisement with `rdnss option (25) ... addr: 2001:db8::53` next to the MTU option (1442) and the prefix. Its lifetime is 4294967295 s (infinite): OVN sends it that way, and CloudX has no setting for it.
  - **A guest uses it**: the CirrOS guest on that `slaac` subnet had `# Generated by dhcpcd from eth0.ra` and `nameserver 2001:db8::53` in `/etc/resolv.conf`, the only resolver it had.
  - **A router port that exists gets it after the restart**: with `rdnss` removed from the router port by hand, `systemctl restart cloudx-networking-api` on one controller put `rdnss="2001:db8::53"` back.
- Not tested: an Ubuntu 24.04 guest (`resolvectl status`; CirrOS showed the path end to end), a `dhcpv6-stateful` subnet with RDNSS, a security group that drops ICMPv6, and an OVN older than 24.03.8 (the `rdnss` key is in the current ovn-nb(5) manual, which does not say which version added it, and `ipv6_ra_configs` is a free string map: an older OVN accepts the setting and may ignore it without an error, so check the advertisement, not only the database).

## Known limitations

- The router advertisement carries one DNS server (OVN's limit), with an infinite lifetime (OVN's choice), and only if the subnet has an IPv6 `--dns`; there is no default IPv6 DNS. `cloudx subnet create --dns-nameserver` takes one value; several need the API.
- A subnet cannot be edited, so adding a gateway to one that was made without means making it again.
- `cloudx server create` takes one `--network`; several networks need the API.
- netplan 1.x warns that `gateway4` and `gateway6` are deprecated. They still work.
- The limits in `docs/quickstart.md` ("Known limitations") and `docs/deb-install.md` section 8 still apply.
