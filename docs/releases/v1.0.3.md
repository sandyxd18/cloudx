# CloudX v1.0.3

CloudX 1.0.3 fixes two things the Ubuntu 24.04 cloud image showed on the lab: the default `user-data` replaced the image's own user with a user called `cirros`, so an Ubuntu server had no `ubuntu` user; and a DHCPv6 client got a /128 and no route, because no router sent router advertisements. There is no schema change and no new service. There are **upgrade steps** (below), and two behaviour changes to read first.

## What is new since 1.0.2

**Compute**
- The default `user-data` (what a server gets when `--user-data` is not given and it has a keypair) keeps the image's own user. It listed `users: [{name: cirros, ...}]`, and a `users:` list without `default` replaces the image's user. It now lists `users: [default]` next to the top-level `ssh_authorized_keys`, which cloud-init gives to the default user: `ubuntu` on an Ubuntu image, `cirros` on CirrOS. Without a keypair the `user-data` is unchanged, and a `user-data` you pass is never touched.

**Networking**
- A router port on an IPv6 subnet sends router advertisements. DHCPv6 gives a client its address but no prefix length and no routes, so a guest that asked DHCPv6 had its address as a /128, no on-link route and no default route, and could not reach its gateway or a neighbour. The advertisement carries the on-link prefix and the router lifetime. Its mode is the subnet's `--ipv6-ra-mode`, else its `--ipv6-address-mode`, else `dhcpv6-stateful`; its MTU is the network's. It is set when a router interface is added, and **router ports that already exist get it when `cloudx-networking-api` starts**, so the upgrade fixes them too. Setting it is best effort: if OVN refuses, the error is logged and the interface is kept, since the static `network-config` still gives a cloud-init guest its address and route. IPv4 subnets are untouched. DNS servers in the advertisement (`rdnss`) are not sent yet.

**Documentation**
- `docs/cloud-init.md` describes the default `user-data`, `docs/ipam.md` the router advertisements.

## Behaviour changes to read first

1. **On an image that is not CirrOS, the keypair belongs to the image's default user.** Before, it belonged to a user called `cirros` on every image. If you ssh'd to `cirros@` on an Ubuntu server, use `ubuntu@` for servers built after the upgrade. Servers that already exist keep the users they have: cloud-init creates users when a server first boots.
2. **Guests on IPv6 subnets with a router now receive router advertisements, existing ones included.** A guest with the static `network-config` accepts them too (netplan's default): the on-link prefix is the same, and it gets a second default route via the router next to its `gateway6`. On a `slaac` or `dhcpv6-stateless` subnet the guest also builds its own address from the prefix, next to the allocated one (the allocated address is sequential, the guest's is derived from its MAC). A security group does not filter the advertisements (checked later, on the 1.0.5~rc1 lab: a port in a group with no ICMPv6 ingress rule still received them); the default group allows ICMPv6 ingress anyway. On the lab this was harmless for a guest with the static `network-config` (see below).

## Upgrading

Order: the controller first, then the compute nodes. Every node must have all of its CloudX packages at one version. The code changes are in `cloudx-networking-api` (controller: the advertisements, set for existing router ports when it starts) and `cloudx-compute-worker` (compute nodes: the `user-data`), but every package takes the new version.

### From 1.0.2 `.deb` packages

1. Download the packages of the release and check them (`docs/deb-install.md` section 3, "Downloading a release").
2. On each node, list what is installed and install the new version of exactly those packages in one command. `--force-confold` keeps your configuration files:

   ```bash
   dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'cloudx-*' | awk '$1 ~ /^ii/ {print $2}'
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-common_*.deb ./cloudx-<each package from the list>_*.deb
   ```

   The package scripts restart the units that were active and leave disabled units disabled. Running VMs are not stopped: QEMU does not run under a CloudX unit.
3. No `cloudx-manage db sync` and no catalog sync are needed. Running them does no harm.
4. `systemctl list-units --failed 'cloudx-*'` must list nothing. Check that the version took: `dpkg-query -W cloudx-common` on each node.

From 1.0.1 or older, do the 1.0.2 upgrade first (`docs/releases/v1.0.2.md`).

## What was tested, and what was not

- The unit and packaging tests pass on the release commit, and CI builds every package. The changes have their own tests: `tests/compute_worker/test_cloud_init.py` (the parsed `user-data` has `users == ["default"]` and the key at the top level, and without a key it has neither; the rendered `user-data` validates with `cloud-init schema`) and `tests/networking/test_ipv6_router_advertisements.py` (the four modes and the address-mode fallback, the network MTU, IPv4 sends none, a refused setting keeps the interface, existing router ports get it at start).
- **1.0.3~rc1 was installed on the lab** (three controllers, two compute nodes, one node at a time from the release `.deb` files): no unit failed and `vm-default` kept running. Checked with the Ubuntu 24.04 image: a server with a keypair and no `--user-data` accepted `ssh ubuntu@` (home `/home/ubuntu`), had no `cirros` user and refused `ssh cirros@`; a CirrOS server built the same way accepted `ssh cirros@`.
- **1.0.3~rc2 was then installed on the same nodes** (the lab is on it) for the router advertisements, which rc1 did not contain. No unit failed and `vm-default` kept running:
  - A router port made while the lab was still on rc1 had no `ipv6_ra_configs`. After the upgrade it had `address_mode=dhcpv6_stateful`, `mtu="1442"` and `send_periodic="true"`: networking-api set it when it started.
  - Router interfaces added on rc2: a `slaac` subnet got `address_mode=slaac`, a `dhcpv6-stateless` one `dhcpv6_stateless`, an IPv4 subnet got nothing.
  - An Ubuntu 24.04 server with the static `network-config` (the default) kept working next to the advertisements: `ping` to the gateway and to a server on another compute node, 0 % loss. Its routes show what to expect: the on-link `/64` learned from the advertisement (`proto ra`, `mtu 1442`) and a default route with two next hops, the static `gateway6` and the router's link-local address.
  - The case that was broken in 1.0.1: the same server with the static configuration removed and only a networkd DHCPv6 client (`DHCP=ipv6`, no `WithoutRA`). It got its allocated address from DHCPv6 (as a /128, as before), and now also the on-link `/64` route and a default route via the router from the advertisement; `ping` to the gateway and to the server on the other node, 0 % loss. With 1.0.1 the same client answered "Network is unreachable".
- Not run: a `slaac` or `dhcpv6-stateless` guest building its own address (the two addresses described above), a security group that drops ICMPv6, and `rdnss` (not sent yet).
- Not tested: evacuation of a multi-network server (1.0.2), and a rebuild of a server that existed before the upgrade.

## Known limitations

- The router advertisements carry no DNS servers (`rdnss`) yet, and CloudX does not allocate the EUI-64 address that a `slaac` guest builds for itself, so such a guest has two addresses.
- `cloudx server create` takes one `--network`; several networks need the API.
- netplan 1.x warns that `gateway4` and `gateway6` are deprecated. They still work.
- The limits in `docs/quickstart.md` ("Known limitations") and `docs/deb-install.md` section 8 still apply.
