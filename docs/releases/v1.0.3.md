# CloudX v1.0.3

CloudX 1.0.3 fixes the users of Ubuntu servers: the default `user-data` replaced the image's own user with a user called `cirros`, so an Ubuntu 24.04 server had no `ubuntu` user. There is no schema change and no new service. There are **upgrade steps** (below), and one behaviour change to read first.

## What is new since 1.0.2

**Compute**
- The default `user-data` (what a server gets when `--user-data` is not given and it has a keypair) keeps the image's own user. It listed `users: [{name: cirros, ...}]`, and a `users:` list without `default` replaces the image's user. It now lists `users: [default]` next to the top-level `ssh_authorized_keys`, which cloud-init gives to the default user: `ubuntu` on an Ubuntu image, `cirros` on CirrOS. Without a keypair the `user-data` is unchanged, and a `user-data` you pass is never touched.

**Documentation**
- `docs/cloud-init.md` describes the default `user-data`.

## Behaviour changes to read first

1. **On an image that is not CirrOS, the keypair belongs to the image's default user.** Before, it belonged to a user called `cirros` on every image. If you ssh'd to `cirros@` on an Ubuntu server, use `ubuntu@` for servers built after the upgrade. Servers that already exist keep the users they have: cloud-init creates users when a server first boots.

## Upgrading

Order: the controller first, then the compute nodes. Every node must have all of its CloudX packages at one version. The only code change is in `cloudx-compute-worker` (compute nodes), but every package takes the new version.

### From 1.0.2 `.deb` packages

1. Download the packages of the release and check them (`docs/deb-install.md` section 3, "Downloading a release").
2. On each node, list what is installed and install the new version of exactly those packages in one command. `--force-confold` keeps your configuration files:

   ```bash
   dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'cloudx-*' | awk '$1 ~ /^ii/ {print $2}'
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-common_*.deb ./cloudx-<each package from the list>_*.deb
   ```

   The package scripts restart the units that were active and leave disabled units disabled. Running VMs are not stopped: QEMU does not run under a CloudX unit.
3. No `cloudx-manage db sync` and no catalog sync are needed. Running them does no harm.
4. `systemctl list-units --failed 'cloudx-*'` must list nothing. Check that the version took: `dpkg-query -W cloudx-common` on each node.

From 1.0.1 or older, do the 1.0.2 upgrade first (`docs/releases/v1.0.2.md`).

## What was tested, and what was not

- The unit and packaging tests pass on the release commit, and CI builds every package. The change has its own tests (`tests/compute_worker/test_cloud_init.py`): the parsed `user-data` has `users == ["default"]` and the key at the top level, and without a key it has neither. The rendered `user-data` validates with `cloud-init schema`.
- **Not run on a cloud yet (rc1).** This section is updated with what the lab shows after 1.0.3~rc1 is installed there. The check: one Ubuntu server and one CirrOS server, each with a keypair and no `--user-data`; `ssh ubuntu@` and `ssh cirros@` respectively must work, and `ssh cirros@` on the Ubuntu server must not. CirrOS is expected to be unaffected (it also gets the key from `public-keys` in `meta-data`), but it has not been booted with this change.
- Not tested: evacuation of a multi-network server (1.0.2), and a rebuild of a server that existed before the upgrade.

## Known limitations

- No router advertisements: a DHCPv6 client gets its address as a /128 and no on-link route or gateway, so it cannot reach its neighbours. Only the static `network-config` makes IPv6 work (see 1.0.1).
- `cloudx server create` takes one `--network`; several networks need the API.
- netplan 1.x warns that `gateway4` and `gateway6` are deprecated. They still work.
- The limits in `docs/quickstart.md` ("Known limitations") and `docs/deb-install.md` section 8 still apply.
