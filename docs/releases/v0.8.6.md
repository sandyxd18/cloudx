# CloudX v0.8.6

Database backup, scheduled backups, Instance HA hardening (watchdog and a second ha-api), an error reaper and a networking fix. There are **upgrade steps**.

## Upgrading from v0.8.5
1. Deploy `services/` to every node and run `cloudx-db-migrate` for `database` (`database_0002` to `database_0004`), `container` (`container_0003`), `file_store` (`file_store_0002`) and `ha` (`ha_0002`), from `/tmp`.
2. Redeploy `database`, `container`, `file-store`, `ha`, `networking`, `shared`, `compute-worker`, `block-store-worker`, the dashboard and the CLI. Restart `cloudx-block-store-worker` on every storage node and `cloudx-compute-worker` on every compute node.
3. Controller: install `cloudx-reaper.service` (runs as root and reads `auth_admin_password` from `cloudx.conf`) and enable it. Optional `/etc/cloudx/reaper/reaper.conf` (`[DEFAULT]`): `reaper_max_age_hours` (24), `reaper_interval` (600), `reaper_dry_run` (false).
4. Every compute node (optional, recommended for protected VMs): create `/etc/cloudx/ha-watchdog/ha-watchdog.conf` (`[DEFAULT]`) with `ha_watchdog_host`, `ha_watchdog_peers` (URLs of the other compute nodes, port 8021, which must be reachable between them) and optionally `ha_watchdog_timeout`; then enable `cloudx-ha-watchdog`.
5. Optional second ha-api: see `docs/ha.md` (`/etc/cloudx/ha-api/ha-api.conf`, a `pg_hba.conf` line for that node, and a comma-separated `ha_api_url` on compute nodes).

## Changes
- **Database backup and restore** (`cloudx database backup create|list|restore|delete`, Backups table in the dashboard): crash-consistent copy of the data volume of a VM + block database. A restore always creates a new instance; the admin password is regenerated and shown once. PostgreSQL and MariaDB restore verified in the lab, including writes during the backup.
- **Behaviour change (all volume backups):** the block-store worker backs up an LVM volume from a temporary snapshot, removed afterwards (also on failure), instead of reading the live LV.
- **Scheduled backups** (`cloudx database backup schedule <instance> --every H --keep N | --off`): cloudx-reaper creates due backups and deletes scheduled backups beyond `keep`. Manual and failed backups are never deleted automatically.
- **Error reaper** (`cloudx-reaper`): deletes Database instances, Containers, Shares and Share networks in `error` that never became ready and are older than the max age, through each service's own DELETE with an admin token. New `ready_at` column (existing rows are set to `created_at`, so nothing that already exists is reaped) and `GET /internal/stale-errors`.
- **HA watchdog** (`cloudx-ha-watchdog`, compute nodes): when ha-api is unreachable for 45 s and the node is isolated, it destroys the protected VMs of its own node before ha-api evacuates them (ha-api acts after 90 s). It does nothing when every peer also lost ha-api, when no peer is configured, or when the protected list is empty. Dry-run mode only logs. A flag file stops compute-worker's auto-recovery from restarting the killed VMs until the operator resets the host. New ha-api endpoints `/internal/protected-domains/{host}`, `/internal/hosts/{host}`, `/internal/watchdog/{host}`.
- **Two ha-api instances**: the monitor loop runs only on the holder of a PostgreSQL advisory lock; the other instance takes over within about 10 s and gives every host a fresh 60 s. `ha_api_url` may list several instances; compute-worker heartbeats to the first that answers and the watchdog counts ha-api as reachable if any answers. ha-api no longer resets `last_seen` on plain startup.
- **iSCSI cleanup after evacuate**: when compute-worker destroys a stale domain (its VM now lives elsewhere), it also logs out the iSCSI sessions of that domain's disks.
- **Fix (networking-api):** concurrent `POST /ports` on one subnet could choose the same free IP in different gunicorn workers; OVN rejected the duplicate (HTTP 502) and left orphan logical switch ports. Allocation now takes a per-subnet PostgreSQL advisory lock until commit. In the lab 16 parallel creates gave 2 successes before and 16 after. This removes the "create containers one at a time" advice of v0.8.5.
- Docs: Manila, Zun, Masakari, Trove and Designate rows in `docs/feature-comparison.md`; `scripts/test-file-store.sh`.

## Known limitations
- **Backup**: only `vm` + `block` (LVM); container, local and file storage are rejected (422). Crash-consistent, not a logical dump: no per-database backup, point-in-time recovery or encryption. Backups outlive their instance. The engine major version must match (restore with the same Ubuntu image). No in-place restore. "Backup in use" protection is in memory and lost when database-api restarts. Tested with an `mc` stand-in, **the real MinIO path was not exercised**. MariaDB restore resets `root@localhost` with `--skip-grant-tables --skip-networking` during first boot.
- **Scheduled backups**: precision about one reaper interval (default 10 min), no fixed time of day. If the reaper is stopped there are no scheduled backups and no retention. Retention counts backups, not age or size. A failed scheduled backup stays until deleted by hand and does not block the next one. No dashboard control.
- **Reaper**: only build failures are reaped; a resource that was ready once and later errored stays. Failed Backups are not reaped. One process on the controller. A delete that keeps failing is retried every pass. It was exercised in the lab on a Container only; Database and File Store are covered by unit tests.
- **Watchdog**: not power fencing (Masakari uses Pacemaker/Corosync with STONITH/IPMI). A frozen kernel or a hung watchdog does not fence itself, and the timing margin (kill at about 45 s, evacuate at 90 s) is not a hard guarantee. Needs at least two compute nodes. If a partition cuts a node from ha-api and every peer, the node kills its protected VMs while ha-api may be unable to evacuate them. The protected list can be a few seconds stale.
- **Two ha-api**: not controller HA. PostgreSQL, compute-api, block-store-api and auth stay on the controller; if it is down the second instance is alive but cannot evacuate. A PostgreSQL connection that dies without closing frees the lock only when the server notices. Failover takes up to one poll (10 s) plus the 60 s host grace. The dashboard knows one ha-api URL. No leader priority. PostgreSQL must accept connections from the second node.
- **iSCSI cleanup**: only sessions of domains that compute-worker destroys as stale; orphan sessions with no domain remain. Verified by unit tests only; a real evacuate was not repeated for this.
- **IP race fix**: only allocation through `allocate_fixed_ip` is serialized; other code that picks addresses itself was not audited. SQLite (tests) has no advisory lock, so unit tests do not reproduce the race.
- Still not done (candidates): File Store snapshots and quotas, Container block volumes and exec, a resource-aware scheduler. The other v0.8.5 limitations stay as listed in `docs/releases/v0.8.5.md`, except "no backup and restore" for Database.
