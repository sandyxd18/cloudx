# CloudX v1.0.11

CloudX 1.0.11 is a patch release after 1.0.10 with three fixes: adding a bandwidth rule to a QoS policy answers `201`, `cloudx object-store object` commands send keys with special characters as typed, and `cloudx-manage policy check` tells an unprivileged user what to do. There is **no schema change** and no configuration change. The changes are in the networking service, the CLI and `cloudx-manage`.

## What is new since 1.0.10

**Networking**
- `POST /qos/policies/{id}/bandwidth_limit_rules` answered `500` (`type object 'Port' has no attribute 'qos_policy_id'`) after it had stored the rule, so the dashboard's "Add bandwidth rule" showed an error for a rule that existed, and a retry stored a second one. It answers `201`. The call tried to apply the rule to the ports that use the policy, but no port refers to a policy (the column was dropped from the port model), so that step is removed: a policy only holds rules, and a port is limited with `qos_max_kbps` and `qos_burst_kbps`. Rules that a failed call left behind stay; delete the duplicates with `DELETE /qos/policies/{id}/bandwidth_limit_rules/{rule_id}`.

**CLI**
- `cloudx object-store object put`, `get` and `delete` quote the key in the URL and `list --prefix` sends the prefix as a query parameter, so a key or prefix with `#`, `?`, `%`, `&` or a space reaches object-store as typed. `put --key 'a b#c.txt'` used to store the key `a b`. The bucket name is quoted as one path segment too.

**cloudx-manage**
- `cloudx-manage policy check` on `/etc/cloudx/policy.yaml` as a user who cannot read it (the directory is `root:cloudx` 750) printed only `Permission denied`; it now adds a line saying to run it with `sudo` or as a user in the `cloudx` group. The exit status is still 1.

## Behaviour changes to read first

1. A bandwidth rule that was stored by a call that answered `500` is still there. Look for duplicates in the policies you used with 1.0.10.
2. An object key that was stored cut at `#` or `?` by an older CLI stays under the cut name.

## Upgrading

From 1.0.10 `.deb` packages: install the new `cloudx-networking-api` on the controllers and `cloudx-common` (it holds `cloudx-manage`) on every node, as in `docs/releases/v1.0.2.md` "Upgrading". Every node must have all of its CloudX packages at one version. No `cloudx-manage db sync`. The `cloudx` CLI is not in the `.deb` files: update it where it is installed (`scripts/install-cli.sh`) to get the object-store fix. Running VMs are not touched.

## What was and was not tested

Unit tests for the three fixes (`tests/networking/test_qos_bandwidth_rule.py`, `tests/cli/test_object_store_quoting.py`, `tests/shared/test_policy_cli.py`).

Lab (2026-11-10, three controllers and two compute nodes): the release files of 1.0.11-rc1 were installed controllers first (the checksums of the 47 `.deb` files matched `SHA256SUMS`). The unit list and states and a hash of `/etc/cloudx` were identical to before on every node, no unit failed, and `vm-default` kept running (the same QEMU process).
- **QoS (1.0.10 first):** on 1.0.10, adding a bandwidth rule answered `500` and left the rule stored. On 1.0.11-rc1, on each controller and through the VIP: two rules added with `201`, the policy held exactly two rules, and a rule and the policy were deleted with `204`.
- **`policy check`:** on ctl01 as a user outside the `cloudx` group, `cloudx-manage policy check /etc/cloudx/policy.yaml` printed the `hint: run it with sudo` line and exited 1; with `sudo` it ran.
- **Object-store CLI:** checked on the wire only, against a local HTTP server, because the lab has no object-store service. `put`, `get` and `delete` of the key `dir/a b#c?d%e&f.txt` in the bucket `b ucket` sent `/buckets/b%20ucket/objects/dir/a%20b%23c%3Fd%25e%26f.txt`, and `list --prefix 'x y#z&q=1'` sent `?prefix=x+y%23z%26q%3D1`. Not run against a real object-store service.
- Not tested: the upgrade from versions before 1.0.10, and a browser.
