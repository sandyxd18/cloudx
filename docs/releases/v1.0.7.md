# CloudX v1.0.7

CloudX 1.0.7 fixes two ways a server lost a NIC without any error: a hard reboot, and a rebuild, rescue or unrescue. Both were found on the lab while testing 1.0.6 and both are in the compute service and the compute worker. There is no schema change, no new service, and no change in the CLI. There are **upgrade steps** (below), and one behaviour change to read first.

## What is new since 1.0.6

**Compute worker**
- `cloudx server reboot --hard` keeps the NICs added after the server was created. The worker destroyed and undefined the domain, then defined it again from the `domain.xml` saved at creation. `attach_interface` writes to the persistent libvirt configuration, so libvirt had the NIC and the saved file did not: after the reboot the server record still listed the port (`extra_port_ids`), its tap stayed in Open vSwitch, and the guest had no such interface. The worker now stops the domain if it runs, drops a managed-save image (so a suspended domain boots instead of resuming), makes sure the unmanaged taps exist, and creates the domain again from the definition libvirt holds. The saved XML is used only when libvirt no longer knows the domain.
- `attach_disk` writes to the persistent configuration in the same way, so a data volume attached after creation was probably lost by the same hard reboot on 1.0.6. That was not reproduced on 1.0.6; on 1.0.7~rc1 a data volume attached after creation survives the hard reboot (see "What was tested").

**Compute API and worker**
- `rebuild`, `rescue` and `unrescue` keep every NIC of a server made with several networks. They defined the domain with the primary tap only, so a two-NIC server came out of each of them with one. The compute API now reads all ports of the server from the networking API and sends them to the worker (the primary port first, then `extra_port_ids` in order), as evacuation already did. The worker defines one NIC per port, makes sure each tap exists before the domain starts, and puts every port in the config drive. The ports are read before the status changes, so an unreachable networking API gives a 502 and leaves the server `ACTIVE`.

## Behaviour changes to read first

1. **The config drive of `rebuild`, `rescue` and `unrescue` now describes the primary port.** Before, the primary port was sent empty and the guest got `dhcp4` on `eth0` only. Now `eth0` is described as it was when the server was created (the static address of the port). For IPv4 the address is the same. For a network with an IPv6 subnet the config drive now carries the port's addresses too, as at creation; before, the guest depended on router advertisements or DHCP alone.

## Upgrading

Order: the controllers first (compute API), then the compute nodes (compute worker). Every node must have all of its CloudX packages at one version. Running VMs are not stopped: QEMU does not run under a CloudX unit.

### From 1.0.6 `.deb` packages

1. Download the packages of the release and check them (`docs/deb-install.md` section 3, "Downloading a release").
2. On each node, list what is installed and install the new version of exactly those packages in one command. `--force-confold` keeps your configuration files:

   ```bash
   dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'cloudx-*' | awk '$1 ~ /^ii/ {print $2}'
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-common_*.deb ./cloudx-<each package from the list>_*.deb
   ```

   The package scripts restart the units that were active and leave disabled units disabled.
3. No `cloudx-manage db sync` and no catalog sync are needed. Running them does no harm.
4. `systemctl list-units --failed 'cloudx-*'` must list nothing. Check that the version took: `dpkg-query -W cloudx-common` on each node.

A compute API of 1.0.6 with a worker of 1.0.7 in the middle of the upgrade behaves as 1.0.6: a worker that gets no `port` and no `ports` makes the primary NIC only. A worker of 1.0.6 with an API of 1.0.7 ignores `ports` (so it still makes one NIC) but already uses `port` for the config drive.

From 1.0.5 or older, do the earlier upgrades first (`docs/releases/v1.0.6.md`, `docs/releases/v1.0.5.md`).

## What was tested, and what was not

- The unit tests pass on the changed code, and CI builds every package. `tests/compute_worker/test_hard_reboot.py` (8 tests), `tests/compute/test_rebuild_rescue_ports.py` (9) and `tests/compute_worker/test_rebuild_extra_nics.py` (11) were written first and failed for the right reason. They run against fake libvirt and HTTP clients, so they show what the code sends and defines, not what libvirt and the guest do with it.
- Both bugs were **reproduced on the lab** on 1.0.6~rc1 (three controllers, two compute nodes): a CirrOS server with a second port attached after creation had one interface after `reboot --hard`; a server made with two `--network` values went from two interfaces in the domain to one after each of `rebuild`, `rescue` and `unrescue`. `vm-default` was not touched.
- **1.0.7~rc1 was installed on the lab** (three controllers, two compute nodes, one node at a time from the release `.deb` files, controllers first; the checksums of the 48 files matched `SHA256SUMS`): all packages at 1.0.7~rc1-1, no unit failed, the unit list and states and a hash of `/etc/cloudx` were identical to before on every node, no traceback in the compute and compute-worker logs, and `vm-default` kept running (the same QEMU process). Checked with CirrOS guests and test resources that were deleted afterwards; the lab was left as it was found:
  - **Hard reboot keeps a NIC added later.** A server on one network got a second port with `server port add --network`; the guest configured `eth1`. Before and after `server reboot --hard` the libvirt domain had two interfaces, live and inactive. The guest had really rebooted (uptime 42 s), `eth0` and `eth1` had their addresses and routes again, and all four logical switch ports of the two test servers were `up`. On 1.0.6~rc1 the same steps left one interface.
  - **Hard reboot keeps a data volume attached later.** A CirrOS server with a Ceph RBD root volume got two 1 GB data volumes after creation, one `ceph-rbd` and one `gp2` (LVM over iSCSI), with `cloudx volume attach`. Before and after `server reboot --hard` the domain had the three disks (`sda`, `sdb`, `sdc`), live and inactive, with the right sources, and the guest saw the three. This was not run on 1.0.6, so the lab does not show that 1.0.6 lost the volume; it shows that 1.0.7 keeps it.
  - **Rebuild, rescue and unrescue keep both NICs.** A server made with `--network a --network b` had two interfaces (live and inactive), `eth0` and `eth1` with their addresses, and two ports `up` after each of `rebuild --image <other image>`, `rescue` and `unrescue`; on 1.0.6~rc1 each of them left one interface. A CirrOS client on another compute node pinged both addresses of the server afterwards, 4/4 on each network, with no loss.
- Lab results for the 1.0.6 code, which is the same as the code of 1.0.6~rc1 (the items `docs/releases/v1.0.6.md` listed as not tested):
  - A dual-stack port on a `slaac` subnet (two CirrOS guests created with `--ipv6`): the port had the IPv4 address and the EUI-64 IPv6 address, which matched the address the guest built itself; each guest had exactly one global IPv6 address and the RDNSS from the router advertisement in `resolv.conf`; ping to the IPv6 gateway, to the other guest and over IPv4 had 0% loss.
  - A port that keeps an explicit IPv6 `fixed_ips` (`::10`; this stands in for a port made before the 1.0.4 upgrade, which the lab does not have) was kept as given, and was unchanged after `systemctl restart cloudx-networking-api`. Hot-plugged into a guest, the guest builds its own EUI-64 address from the MAC, not `::10`. With two NICs on one subnet the guest sent the reply out of the wrong NIC (multihoming) and the ping was lost; with the routes on `eth1` only, the EUI-64 address answered 4/4. Put the NICs of a server on different subnets.
  - A rebuild of a one-NIC server: `ACTIVE` in 8 s, the same NIC and the same addresses, no stale-domain destroy and no extra `Claiming` lines.
- Not tested: an OVN older than 24.03.8. It is outside the supported platform (see "Known limitations").

## Known limitations

- **OVN version.** OVN comes from the Ubuntu 24.04 archive; CloudX packages do not ship or pin it. The lab tests of 1.0.5 to 1.0.7 ran on 24.03.8 (`ovn-central` and `ovn-host` from `noble-updates`). An older OVN is **outside what CloudX is tested on**. Nothing in CloudX checks the version, and `ipv6_ra_configs` is a free string map: an older OVN may accept the router-advertisement settings (such as the `rdnss` key of 1.0.5) and ignore them without an error, so on such a host check the advertisement a guest receives, not only the database.
- The limits of `docs/releases/v1.0.6.md` and `docs/releases/v1.0.5.md` still apply.
