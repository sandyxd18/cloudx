# CloudX v1.0.4

CloudX 1.0.4 fixes two things the 1.0.3 lab showed: after an evacuation the compute node that still had the old domain kept its taps, and OVN on the two nodes then fought over the port; and a guest on a `slaac` or `dhcpv6-stateless` subnet built an address of its own that CloudX did not know. There is no schema change and no new service. There are **upgrade steps** (below), and two behaviour changes to read first.

## What is new since 1.0.3

**Compute**
- When a compute node finds a domain whose server now lives on another host (the cleanup after an evacuation), it deletes the taps of that domain together with the domain. Before, the domain was destroyed and its taps stayed in Open vSwitch. A leftover tap keeps its `iface-id`, so `ovn-controller` on that node and on the new host both claimed the port: about 60 claims a minute on each node, and the port's chassis in the Southbound database flipping between the two every ~2 s. Traffic to the server from other nodes is unreliable while that goes on. The delete, rollback and detach paths already removed taps; only this one did not.

**Networking**
- On a subnet whose `--ipv6-address-mode` is `slaac` or `dhcpv6-stateless`, a new port gets the EUI-64 address of its MAC (RFC 4291 appendix A), which is the address the guest builds for itself from the advertised prefix. The port, the server record, the OVN addresses and the guest agree on one address. Before, CloudX allocated the next sequential address: an Ubuntu guest then had two global addresses, and a CirrOS guest (which ignores `network-config` for IPv6) had only the EUI-64 one, so the address CloudX showed was not on the guest at all. If the EUI-64 address is taken, or is the gateway (one chance in 2^40 with a random MAC), the port gets another MAC; after 8 tries the request fails with 409.
- `cloudx subnet create` with one of those two address modes and a prefix that is not a /64 is refused with 400, since the interface id is 64 bits.

**Documentation**
- `docs/ipam.md` describes the EUI-64 allocation.

## Behaviour changes to read first

1. **A new port on a `slaac` or `dhcpv6-stateless` subnet gets the EUI-64 address, not the next sequential one.** Ports that exist keep what they have, so a server built before the upgrade still has two addresses on Ubuntu; make its port again (or the server) to get the EUI-64 one. An address named in `fixed_ips` is kept as given, and the guest then has two. `dhcpv6-stateful` subnets, subnets with no mode, IPv4 and router ports are unchanged.
2. **`subnet create --ipv6-address-mode slaac|dhcpv6-stateless` on a prefix other than /64 is refused.** Existing subnets of another size are not touched and keep counting up.

## Upgrading

Order: the controller first, then the compute nodes. Every node must have all of its CloudX packages at one version. The code changes are in `cloudx-networking-api` (controller: the EUI-64 allocation and the /64 rule) and `cloudx-compute-worker` (compute nodes: the tap cleanup), but every package takes the new version.

### From 1.0.3 `.deb` packages

1. Download the packages of the release and check them (`docs/deb-install.md` section 3, "Downloading a release").
2. On each node, list what is installed and install the new version of exactly those packages in one command. `--force-confold` keeps your configuration files:

   ```bash
   dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'cloudx-*' | awk '$1 ~ /^ii/ {print $2}'
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-common_*.deb ./cloudx-<each package from the list>_*.deb
   ```

   The package scripts restart the units that were active and leave disabled units disabled. Running VMs are not stopped: QEMU does not run under a CloudX unit.
3. No `cloudx-manage db sync` and no catalog sync are needed. Running them does no harm.
4. `systemctl list-units --failed 'cloudx-*'` must list nothing. Check that the version took: `dpkg-query -W cloudx-common` on each node.
5. **Taps left by an earlier evacuation stay on the node**, because the domain they belonged to is already gone and the cleanup only looks at domains it finds. On each compute node, compare the taps in Open vSwitch with the taps of the running domains:

   ```bash
   sudo ovs-vsctl list-ports br-int | grep '^tap-mini-' | sort > /tmp/ovs-taps
   for d in $(sudo virsh list --name); do sudo virsh domiflist "$d" | awk '$2 == "ethernet" {print $1}'; done | sort > /tmp/domain-taps
   comm -23 /tmp/ovs-taps /tmp/domain-taps
   ```

   Every name that command prints belongs to no running domain on that node. Check that its server runs elsewhere (or is gone), then remove it with `sudo ovs-vsctl del-port <tap>` and `sudo ip link delete <tap>`. A node whose server was evacuated and whose old taps are still there is the one that shows the port claims described above (`grep -c Claiming /var/log/ovn/ovn-controller.log`).

From 1.0.2 or older, do the earlier upgrades first (`docs/releases/v1.0.3.md`, `docs/releases/v1.0.2.md`).

## What was tested, and what was not

- The unit and packaging tests pass on the release commit, and CI builds every package. The changes have their own tests: `tests/compute_worker/test_stale_domain_taps.py` (the taps come from the domain XML, they are deleted after the domain and only for a stale one, an unreadable or undeletable tap stops nothing) and `tests/networking/test_ipam.py` plus `tests/networking/test_eui64_ports.py` (the RFC 4291 vector, the address two lab guests built from their MAC, which subnets qualify, a taken address or the gateway draws a new MAC, the /64 rule, the OVN address, an address named in `fixed_ips` kept, dual-stack, other modes unchanged).
- **The problems were measured on the 1.0.3 lab** (three controllers, two compute nodes), and that is where the fixes come from:
  - A CirrOS server on two networks with a Ceph-RBD root volume was evacuated from comp02 (marked `forced_down`, the host itself alive) to comp01: `ACTIVE` in about 12 s with both NICs, both taps, both ports installed in OVN. On comp02 both taps stayed in Open vSwitch, both nodes logged about 60 `Claiming` lines a minute, and the chassis of both ports flipped every ~2 s. Removing the two taps by hand stopped it at once (no claims in 10 s) and a guest on the other node pinged both addresses of the evacuated server with no loss. A ping from a guest on the same node as the evacuated server worked throughout, so it does not show the problem.
  - On a `slaac` and on a `dhcpv6-stateless` subnet behind a router, Ubuntu 24.04 and CirrOS guests built the EUI-64 address of their MAC (`addr_gen_mode` 0, no temporary addresses). Ubuntu also kept the sequential address from `network-config`; CirrOS had only the EUI-64 one.
- **1.0.4~rc1 was installed on the lab** (three controllers, two compute nodes, one node at a time from the release `.deb` files): all packages at 1.0.4~rc1-1, no unit failed, the unit list and states and a hash of `/etc/cloudx` were identical to before on every node, and `vm-default` kept running (the same QEMU process). Checked on it:
  - **Evacuation of a server on two networks with the source host still alive** (the case that flapped on 1.0.3): CirrOS, Ceph-RBD root volume, comp02 marked `forced_down`, then evacuated to comp01. `ACTIVE` in about 19 s with both NICs. About 35 s later the compute worker on comp02 logged `destroying stale domain` and ran `ovs-vsctl del-port` for both taps; comp02 then had no domain, no tap in Open vSwitch and none in the kernel, and both ports were bound to comp01. The `Claiming` lines for the two ports ran from the start of the evacuation to the moment the taps were deleted (about 30 s, until the worker's next reconcile pass found the stale domain) and **there were none after that**; on 1.0.3 they went on at about 60 a minute on each node for as long as the taps stayed. A guest on comp02 pinged both addresses of the evacuated server with no loss.
  - **EUI-64 allocation**, on a `slaac` and on a `dhcpv6-stateless` subnet behind a router, with a CirrOS and an Ubuntu 24.04 server on each: the port's `ipv6_address` was the EUI-64 address of its MAC, `cloudx server list` showed the same, and every guest had **exactly one** global IPv6 address, equal to it (Ubuntu had two on 1.0.3). The Ubuntu guests reached their gateway with no loss. `subnet create --ipv6-address-mode slaac` on a /80 was refused with 400 and the message from this release.
- Not tested: the evacuation of a server with one NIC (the same code path, not run), a rebuild of a server that existed before the upgrade, a port that existed before the upgrade (it keeps its address by design), a dual-stack port on a `slaac` subnet, and a security group that drops ICMPv6 on a `slaac` subnet.

## Known limitations

- The router advertisements carry no DNS servers (`rdnss`) yet.
- `cloudx router add-interface` on an IPv6 subnet that was created without a gateway fails with HTTP 502 (`ovn-nbctl: invalid network address: /64`); give the subnet a `--gateway` first.
- `cloudx server create` takes one `--network`; several networks need the API.
- netplan 1.x warns that `gateway4` and `gateway6` are deprecated. They still work.
- The limits in `docs/quickstart.md` ("Known limitations") and `docs/deb-install.md` section 8 still apply.
