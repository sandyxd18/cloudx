# CloudX v1.0.10

CloudX 1.0.10 confirms a resize that nobody confirmed, replaces the browser console link that pointed nowhere with a noVNC proxy on every compute node, adds domain and system scoped tokens, application credential rotation and trusts, adds three dashboard pages, puts the admin-only actions of every service under an operator-editable policy file, and tightens access checks: the roles of an application credential, the lookup of an application credential, a domain's consolidated invoice, who may change an image, and who may call the bulk usage and metric routes. The changes are in the compute service, the reaper, the compute worker, the identity service, billing, telemetry, the image service, the other services' admin gates, the dashboard and the packaging. There are **three schema changes** and **upgrade steps** (below), and several behaviour changes to read first.

## What is new since 1.0.9

**Compute API and reaper**
- **A resize is confirmed automatically.** `cloudx-reaper` confirms a server that has waited in `VERIFY_RESIZE` longer than `RESIZE_CONFIRM_WINDOW_SECONDS` (86400 by default; `0` turns it off), through the public `confirmResize`. The reaper runs every `REAPER_INTERVAL` seconds (600), so the confirmation comes up to one interval after the window. `REAPER_DRY_RUN` only logs. compute-api has `GET /internal/resize-pending?seconds=N` for the sweep, and the server record has a new column, `resize_pending_since` (migration `compute_0005`), set by the conductor while the status is `VERIFY_RESIZE`. A server that an older version left `ACTIVE` with a rollback snapshot is not swept.

**Compute worker and packaging**
- **The browser console goes through a proxy on the compute node.** A new unit, `cloudx-novnc-proxy`, runs `websockify` and the noVNC client on port 6080 of every compute node. `console-url` and `remote-consoles` return `http://<console_proxy_host>:6080/vnc.html?autoconnect=1&path=websockify%3Ftoken=<token>`. The guest's VNC stays on `127.0.0.1`. The token is a JWT signed with a key derived from `auth_secret_key`, valid 300 seconds, and good for one VNC port of one libvirt domain on that node (`COMPUTE_HOST`); the proxy checks the signature and the expiry when the connection opens, then asks libvirt whether the domain still owns the port, and logs every refusal with its reason (never the token). Before, the link was `NOVNC_BASE_URL?host=localhost&port=<vnc port>`, and nothing in the packages started a proxy.
- The proxy ships in the `cloudx-compute-worker` package, which now depends on `novnc`. The worker's unit has `Wants=cloudx-novnc-proxy.service` and the proxy unit has `PartOf=cloudx-compute-worker.service`, so the proxy starts, restarts and stops with the worker; the package does not enable it on its own. On a tarball node the example worker unit of `docs/tarball-install.md` has the same line and its start command enables the proxy. `console_proxy_host` in `/etc/cloudx/compute-worker/compute-worker.conf` sets the address that goes into the link (default: the node name). See `docs/console.md`.

**Identity**
- **Domain and system scoped tokens.** `POST /auth/tokens` takes `scope` with one of `{"project": ...}`, `{"domain": ...}` or `{"system": true}`. A domain token (for a domain admin of that domain, or an admin) has no project; only auth-api and billing accept it, every other service answers 403 `project-scoped token required`. A system token needs the admin role.
- **Application credential rotation.** `POST /v3/users/{user}/application_credentials/{cred}/rotate` with an optional `grace_seconds` (0 to 86400), during which the replaced secret still works, and `cloudx auth appcred rotate USER CRED [--grace-seconds N]` (migration `auth_0008`).
- **Trusts.** `POST|GET /v3/OS-TRUST/trusts`, `GET|DELETE /v3/OS-TRUST/trusts/{id}` and `POST /auth/tokens/trust` (migration `auth_0009`). A trustor delegates roles it holds in one project to another user; the trustee exchanges the trust for a token that acts as the trustor. Each exchange is written to the audit log as `trust.token`. The whole feature is described in `docs/identity.md`.
- **The roles of an application credential are checked.** `roles` must be a non-empty list without duplicates from `admin`, `member` and `reader` (400 otherwise), and the credential's user must hold every one of them in their project (403 otherwise; `admin` covers `member` and `reader`). When an admin creates a credential for another user, the roles are checked against that user. If `roles` is left out, the credential gets `["member"]`, or the user's own role when they do not hold `member`. The check is repeated at every login: the token gets the credential's roles that the user still holds at that moment, and the login answers 401 when none is left. This also applies to credentials created by earlier versions, with no migration.
- **An application credential is reached through its own user only.** `GET` and `DELETE /v3/users/{user}/application_credentials/{cred}` looked a credential up by id without checking its owner. They now look it up among the URL user's own credentials and answer 404 for another user's credential, as rotate already did. A login by `application_credential_name` alone now tries the enabled credentials of that name, at most 5 in the order they were created, and accepts the one whose secret fits; before, it took the first credential of that name and failed when it belonged to another user. A login by id is unchanged.

**Policy file**
- **`/etc/cloudx/policy.yaml` decides the admin-only actions of every service.** 57 actions: the 22 of `auth-api` and 35 more (12 of compute, 8 of block-store, 5 of placement, 3 of billing, 2 each of telemetry, networking and object-store, 1 of ha). A rule is a boolean expression of `role:NAME`, `domain_admin:True|False`, `rule:NAME`, `@`, `!`, `and`, `or`, `not`. Without the file every decision is what it was; a bad rule or file never stops a service. The file is re-read within 2 seconds of a change. `cloudx-manage policy check [FILE]` validates a file and `cloudx-manage policy defaults` prints the built-in rules. The sample is `/usr/share/cloudx/policy.yaml.sample` in `cloudx-common`; no package creates `/etc/cloudx/policy.yaml`. Ownership, visibility and state checks, `/internal/...` routes and the four bulk billing and telemetry routes stay in code. See `docs/policy.md`.

**Image**
- **Changing an image needs its owner.** `PATCH`, `DELETE`, `deactivate`, `reactivate`, tags and sharing on `image-api` now require the image's owner, an admin of the owner's domain, or a system admin (the internal token counts as one, so `image-worker` is unchanged). The fields the service manages itself (`status`, `size`, `checksum`, `object_name`, `filename`, `storage_backend`) can be set by an admin or the internal token only, and the file store serves only files inside its folder. **Upgrade soon.**

**Billing and telemetry**
- **The bulk usage and metric calls need an admin or the internal token.** `POST /billing/usage-records/batch`, `POST /billing/cleanup`, `POST /telemetry/metrics/batch` and `DELETE /telemetry/metrics/cleanup` have accepted any signed-in user since 0.7.18. The billing and telemetry workers call them with the internal token and are not affected.

**Billing**
- **A domain's consolidated invoice is limited to the system admin and that domain's admin.** `GET /billing/invoices?domain_id=<id>` added `domain:<id>` to the filter for any caller, so it could return the invoices of a domain the caller does not administer. It now does so only for the system admin and for the admin of that domain; other callers get no domain invoice. `POST /billing/invoices?domain_id=<id>` answers 403 when the caller is a domain admin of another domain.

**Dashboard**
- New pages for Trunks, QoS policies and Subnet pools under Networking.

## Behaviour changes to read first

1. **A resize no longer waits forever in `VERIFY_RESIZE`.** After `RESIZE_CONFIRM_WINDOW_SECONDS` (86400 s, one day) the reaper confirms it, within one `REAPER_INTERVAL` (600 s) after that. The statement of 1.0.9 that there is no automatic confirm no longer holds. A script or operator that wants to revert a resize must do it inside the window, or set `RESIZE_CONFIRM_WINDOW_SECONDS=0` in the reaper's environment to keep the old behaviour. Servers that are in `VERIFY_RESIZE` at the upgrade get a full window from the upgrade (the migration sets their start time to its own time).
2. **The browser console needs more on every compute node.** The `novnc` package (installed by the `cloudx-compute-worker` package; `sudo apt install novnc` on a tarball node, which also needs `cloudx-novnc-proxy` enabled and started); port 6080/tcp reachable from your users' browsers; `console_proxy_host` set to an address a browser can reach, or the link holds the node name; `auth_secret_key`, which the proxy reads from `/etc/cloudx/cloudx.conf` (the file copied from the controller, as for the worker); `COMPUTE_HOST` equal for the worker and the proxy; and the python `libvirt` binding in the same venv as the worker (the `libvirt-python` line of the worker's requirements puts it there). `websockify` pulls `numpy`, `jwcrypto` and `redis` into the venv of every node. `NOVNC_BASE_URL` is no longer read. A console link is a token valid for 300 seconds and is checked when the connection opens, so a console page that stays open for more than 5 minutes before it connects needs a reload, and a link made by an older compute-api (`...?host=localhost&port=...`, no token) is not accepted by the proxy. During the upgrade, a new compute-api with a compute worker that is not upgraded yet returns `novnc_url: null` from `console-url`, because the old worker does not say which proxy address and libvirt domain to use; it works again once the worker on that node is upgraded.
3. **Application credentials get no more roles than their user holds.** Creating one with a role the user does not hold now answers 403, and an empty list, a repeated role or an unknown role name answers 400. At login the token carries only the roles the user still holds, and the login answers 401 when none is left. An existing credential that carries a role its user does not hold therefore gets fewer roles, or stops working. Automation that used such a credential must get a new credential (or a rotation) with roles that the user holds, or the user needs the role. A create call with no `roles` gets `member` (or the user's own role when it does not hold `member`).
4. **Another user's application credential answers 404 on `GET` and `DELETE`.** A script that showed or deleted a credential through a user reference other than the owner now gets 404; use the owner's user. A login by `application_credential_name` alone tries up to 5 enabled credentials with that name; give the id when there are more.
5. **A domain's consolidated invoice is for the system admin and that domain's admin only.** `GET|POST /billing/invoices?domain_id=<id>` from anyone else no longer returns or creates it (list: no domain invoice; create: 403).
6. **Domain-scoped tokens and trust tokens have limits.** A domain-scoped token is accepted by auth-api and billing only; every other service answers 403 `project-scoped token required`. A token issued from a trust is read-only against auth-api (logout excepted), never outlives its trust, and keeps working until it expires when the trust is revoked afterwards: revoking a trust stops new exchanges but does not revoke tokens already issued from it. Give a trust a short `expires_at` and a small `remaining_uses`.
7. **Schema changes.** `compute_0005` (`compute_servers.resize_pending_since`), `auth_0008` (`previous_secret_hash` and `previous_valid_until` on application credentials) and `auth_0009` (the `auth_trusts` table). Run `cloudx-manage db sync` (see below). This was one schema change in 1.0.9.
8. **The file of rules now matters on every node.** If you use a policy file, it must exist, identical, on every node that runs any API service (until now only `auth-api` nodes read it). A rule of `"!"`, or one without `role:admin`, on `compute:service:update` or `compute:server:evacuate` stops HA recovery, because the HA monitor's internal token is checked by the same rule; `compute:quota:set` also needs `identity:project:quota-set` to allow. Run `cloudx-manage policy check` on each node.
9. **A denied request on the converted admin routes answers `403` with `Policy does not allow <action>`** instead of `admin role required`. Who is allowed does not change unless a policy file says so.
10. **Only the owner, an admin of the owner's domain or a system admin changes an image,** and the bulk billing and telemetry routes answer `403` to other users. A script that did either as an ordinary user must use the owner's account or an admin.

## Upgrading

Order: the controllers first (compute API, auth, billing, reaper), then the compute nodes (compute worker, with the new proxy unit). Every node must have all of its CloudX packages at one version. Running VMs are not stopped: QEMU does not run under a CloudX unit.

### From 1.0.9 `.deb` packages

1. Download the packages of the release and check them (`docs/deb-install.md` section 3, "Downloading a release").
2. On each node, list what is installed and install the new version of exactly those packages in one command. `--force-confold` keeps your configuration files:

   ```bash
   dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'cloudx-*' | awk '$1 ~ /^ii/ {print $2}'
   sudo apt install -o Dpkg::Options::=--force-confold ./cloudx-common_*.deb ./cloudx-<each package from the list>_*.deb
   ```

   The package scripts restart the units that were active and leave disabled units disabled. On a compute node apt installs the `novnc` package as a dependency of `cloudx-compute-worker` and installs the proxy unit; the worker's unit now has `Wants=cloudx-novnc-proxy.service`, so the proxy starts when the worker restarts.
3. Right after the packages are installed on the first controller (the one with `cloudx-db`), apply the schema changes:

   ```bash
   sudo cloudx-manage db sync
   ```

   It is safe to run again. Until it has run, the compute API selects `resize_pending_since`, a column the table does not have, so requests that read servers fail, and auth selects the two new columns of application credentials, so requests that read application credentials fail, and the trust endpoints have no table. The window is the time between the package install and this command, so run it at once.
4. On each compute node: open port 6080/tcp to your users' browsers, set `console_proxy_host` in `/etc/cloudx/compute-worker/compute-worker.conf` (`[DEFAULT]`) to an address they can reach, and restart `cloudx-compute-worker`. Check with `systemctl is-active cloudx-novnc-proxy` (`docs/deb-install.md` section 4.2, step 6, and `docs/console.md`).
5. No catalog sync is needed. `systemctl list-units --failed 'cloudx-*'` must list nothing. Check that the version took: `dpkg-query -W cloudx-common` on each node.

### From a tarball install

The tarball install is the legacy path (`docs/tarball-install.md`); the steps below come from that guide and were not tried for this release. On each node, extract the release tarball to `/opt/cloudx`, run `pip install -r /opt/cloudx/requirements.txt` and `pip install /opt/cloudx/services --no-deps` in `/opt/cloudx/venv`, copy `etc/systemd/*.service` to `/etc/systemd/system/` and run `systemctl daemon-reload`. On the first controller apply the schema with `sudo CLOUDX_SERVICES_DIR=/opt/cloudx/services /opt/cloudx/venv/bin/cloudx-manage db sync` (`cloudx-db-migrate`, section 2.5 step 6 of the guide, applies the same migrations), then restart the units, controllers first. On each compute node also: `sudo apt install novnc`; make sure `/etc/cloudx/cloudx.conf` (with `auth_secret_key`) is on the node; give the proxy the same `COMPUTE_HOST` as the worker (a `compute_host` line in `/etc/cloudx/compute-worker/compute-worker.conf` serves both); add `Wants=cloudx-novnc-proxy.service` to a worker unit written by hand, and `sudo systemctl enable --now cloudx-novnc-proxy`; open port 6080/tcp. Without `/usr/share/novnc` the proxy unit is skipped without an error and nothing listens on port 6080.

During the upgrade, between the first controller and the last compute node, avoid opening a console of a server on a node that is not upgraded: a new compute-api returns `novnc_url: null` for it (above). These mixed-version cases come from reading the code; they were not tried.

From 1.0.8 or older, do the earlier upgrades first (`docs/releases/v1.0.9.md`, `docs/releases/v1.0.8.md`).

## What was and was not tested

- The unit and integration tests pass: `pytest -q` gave 2005 passed, 65 skipped on the commit of this release candidate, with #105 to #114 merged. The CI `deb` job, which builds the packages and checks their contents, passes. The tests run against fake libvirt, HTTP clients, RPC and a sqlite database, so they show what the code sends, defines and answers, not what libvirt, a browser or Postgres do with it. The changes of #106, #107 and #108 each have new tests that failed on the old code.
- **Nothing in this release has been run on the lab yet.** This release candidate exists to be installed there. The following are what it has to show:
  - Resize auto-confirm with a short `RESIZE_CONFIRM_WINDOW_SECONDS`, and the conductor SQL that sets `resize_pending_since` on Postgres (the `CASE`/`COALESCE` update and the timestamp bound as a string ran on sqlite only).
  - The console of a VM on the controller and of a VM on another compute node: that a browser reaches port 6080, that `COMPUTE_HOST` agrees between the worker and the proxy on `.deb` and on tarball nodes, the real unit with `/usr/share/novnc`, and that a console tab left idle for more than 5 minutes needs a reload.
  - The Trunks, QoS policies and Subnet pools pages in a browser. They were built with a Windows `node` on a copy of the frontend, because `node_modules` in the checkout only has win32 rollup binaries.
  - A domain scoped login and a system scoped login, a rotation with `--grace-seconds`, and a trust created and redeemed end to end.
  - The policy file on a real node set: `cloudx-manage policy check` on each node, a rule that opens or closes one action (for example `compute:flavor:create`), the change taken without a restart, and HA recovery (`compute:service:update`, `compute:server:evacuate`) with the file in place.
  - The upgrade itself from 1.0.9: `cloudx-manage db sync` with the three migrations, a server already in `VERIFY_RESIZE`, and the mixed-version cases above.
- Not planned for this release: live migration, and QoS enforcement on LVM volumes.

## Known limitations

- **Live migration is not built** (`POST /servers/{ref}/live-migrate` answers 501). Use cold migration.
- **Revoking a trust does not revoke the tokens already issued from it.** They expire with the trust, or after `AUTH_TOKEN_EXPIRE_HOURS`.
- **The console link is plain `http`.** The proxy has no TLS. websockify logs rejected tokens and the URLs of its access lines itself; the tokens live 300 seconds.
- **A server snapshot images the root volume only,** as in 1.0.8.
- **OVN version.** As in `docs/releases/v1.0.7.md`: OVN comes from the Ubuntu 24.04 archive; the lab tests ran on 24.03.8 (`noble-updates`). An older OVN is outside what CloudX is tested on.
- The limits of `docs/releases/v1.0.8.md`, `docs/releases/v1.0.7.md` and `docs/releases/v1.0.6.md` still apply.
